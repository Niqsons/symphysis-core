# symphysis-edge-probe

Проба краёв шага `specs` схемы symphysis: по каждому требованию —
конкретные края, которых требование не оговорило. Механика — из GSD
Core: закрытая таксономия восьми категорий, фильтр применимости и отказ
только с причиной (`upstream/gsd-core/gsd-core/references/edge-probe.md:62-90`),
конкретный край вместо напоминания и четыре исхода
(`workflows/spec-phase.md:344-352`, Step 5.5). Оригинал целиком —
`references/edge-probe.md`; где смысл инструкции изменён против
источника — `TRANSLATION-NOTES.md`.

## Главное правило

**Решает человек, не модель.** Модель называет форму требования,
проходит категории и пишет кандидата с четырьмя вариантами — а исход
появляется только из слова человека: `decision` пишет `apply`,
`outcome` — его зеркало. **Отказ без причины не принимается**:
«Dismissal requires a reason string. "N/A — input is a bounded enum,
no boundary exists" is valid; silence is not» (`edge-probe.md:89-90`);
`check` красит Dismiss без причины.

**Каждая пара получает строку.** На требование — восемь строк файла
покрытия, по одной на категорию: так «не нашли», «нашли, но не вынесли»
и «не смотрели» различимы. Человеку идут только кандидаты. Файл покрытия
скрипт не разбирает: пропущенную пару никто не назовёт, счёт держишь сам.

**Край — конкретный, не напоминание.** «Подумать о границах» —
не кандидат; «R2 сливает интервалы — что с `[[1,2],[2,3]]`, которые
только касаются?» — кандидат (`spec-phase.md:344-345`). Напоминание
называет тему, край называет данные и вопрос о них: нечего подставить
в требование — это напоминание, край ещё не найден.

**Зачем проба стоит до кода.** Проверяющий видит только записанные
утверждения: на краях, которых спека не назвала, он уверенно ошибается
(«~0.93 confidence while catching 0/12 omitted-edge defects»,
`edge-probe.md:20`). Лечится не проверяющим, а полнотой спеки: край
становится сценарием до того, как появился код.

## Файлы и команды

`<каталог изменения>` — `openspec/changes/<имя>/`. Вход: требования —
`<каталог изменения>/specs/<capability>/spec.md`, журнал —
`<каталог изменения>/decisions.json` (тот же, что вёл брейншторм;
кандидаты получают следующие номера F-NN). Выход: файл покрытия
`<каталог изменения>/edge-probe.md`, кандидаты в журнале, след в spec.md,
строка итога в `notes[]`.

```bash
# состав: один вызов в начале пробы
python .symphysis/tools/symphysis_config.py

# после каждой записи: схема и правила (код 1 — журнал негоден, чини), улики (сигнал)
python .symphysis/tools/journal.py check <каталог изменения>/decisions.json
python .symphysis/tools/journal.py render-md <каталог изменения>/decisions.json --out <каталог изменения>/decisions.md

# круг просмотрщика: человек решает в HTML, промпт возврата вносит apply
python .symphysis/tools/journal.py render-html <каталог изменения>/decisions.json --out <каталог изменения>/decisions.html
python .symphysis/tools/journal.py apply <каталог изменения>/decisions.json <каталог изменения>/answers/<дата>.md
```

Непонятно, что делает скрипт, когда его звать или что значит код выхода, —
зови `--help` этого скрипта или подкоманды (`journal.py <подкоманда> --help`),
а файл скрипта не читай.

JSON правят только модель (кандидаты, `outcome`, `consequences`,
`notes`) и `apply` (слово человека). `spec.md` модель правит только
по решённому исходу и следом пробы. `decisions.md` и `decisions.html` —
рендер, в них не пишут.

## Порядок пробы

Сквозной пример — требование capability `busy-report`, формы `collection`
и `stateful`:

```markdown
### Requirement: Отчёт сливает интервалы занятости
Система SHALL сливать пересекающиеся интервалы занятости сотрудника и записывать итог в файл отчёта.

#### Scenario: Пересекающиеся интервалы
- **GIVEN** интервалы `[[1,3],[2,4]]`
- **WHEN** собирается отчёт
- **THEN** в файле отчёта один интервал `[1,4]`

#### Scenario: Одна сборка за раз
- **GIVEN** сборка отчёта уже идёт
- **WHEN** запускается вторая сборка
- **THEN** вторая завершается отказом, файл отчёта не тронут
```

### 1. Узнай состав

Зови `symphysis_config.py` один раз, до всего остального. Вывод:

```text
[..] symphysis.yaml: ветки отказа вкл, допущения вкл, проба краёв вкл
```

Пробе нужна последняя часть. `проба краёв вкл` — такт 2. `проба краёв
выкл` — такт 11, и на этом проба кончается.

Файл `symphysis.yaml` не читай и не правь: значение `no` там пробу
не выключает, а модель прочла бы его как выключение. Человеку вопрос
о составе не задавай. Правка файла после вызова действует со следующего
запуска, поэтому второй раз скрипт не зови.

Строка `[!!]` под составом (недопустимое значение, файл не разбирается,
нет пакета PyYAML) пробу не останавливает: при сомнении скрипт считает
пробу включённой, и напечатанный состав это уже учитывает. Иди по составу,
файл не чини, строку `[!!]` дословно передай человеку. Скрипт не запустился
или его нет — считай пробу включённой и скажи об этом человеку.

### 2. Вход

В счёт идут `### Requirement:` из секций `## ADDED Requirements`
и `## MODIFIED Requirements` всех `specs/**/spec.md` изменения. Снятые
и переименованные (`## REMOVED Requirements`, `## RENAMED Requirements`)
строк и кандидатов не получают: поведения, которое можно уточнить, у них
нет. Таких требований нет вовсе — в файле покрытия заголовок и строка
`требований в счёте нет`, кандидатов нет. Нет ещё spec.md (скилл позван
раньше) — вход: решённые записи журнала, у которых `consequences` называет
поведение.

Ключ требования — `<capability>/<имя требования>`: capability — имя каталога
под `specs/`, имя — текст после `### Requirement: `. Пример: `busy-report/Отчёт
сливает интервалы занятости`. Одно имя в двух capabilities — это два требования
и шестнадцать строк: без capability в ключе их строки слились бы.

Требование читается как есть, на русском: перевода и cue-слов нет, форму
называет модель по смыслу (`edge-probe.md:52` «The classifier reads English;
`text` does not have to be.»). Проба идёт по ясным требованиям
(`spec-phase.md:193`): вопрос «что требование значит» — не край,
а развилка брейншторма.

### 3. Назови форму

Пять форм (`edge-probe.md:47`), у требования одна или несколько:

| Форма | Признак |
| --- | --- |
| `numeric-range` | число с границей, порогом, округлением |
| `collection` | список, множество, интервалы, записи |
| `text` | строка: длина, равенство, нормализация |
| `stateful` | меняет состояние: запись, повтор, отмена |
| `io` | граница системы: файл, сеть, процесс, прерывание |

Форма называется всегда. Требование о строке или числе, где нет записи,
повтора, отмены, файла, сети и процесса, — только `text` или `numeric-range`:
лишняя форма даёт лишние вопросы. Требованию, которому не подошла ни одна
форма, ставь `stateful` или `io`: наблюдаемое поведение хотя бы меняет
состояние или пересекает границу, лишнего кандидата человек отведёт с причиной.
Форма пишется в префикс вопроса записи; человек правит её там же.

### 4. Пройди восемь категорий

Каждому требованию — все восемь строк таблицы. Таблица GSD дословно
(`edge-probe.md:70-79`), перевод рядом:

| id | name (QA term) · по-русски | applies to shapes | probe question · по-русски |
| --- | --- | --- | --- |
| boundary | Boundary values · граничные значения | numeric-range | What happens exactly at each min/max/threshold — and one step either side? · Что происходит ровно на каждом min/max/пороге — и на шаг в обе стороны от него? |
| adjacency | Adjacency / touching · смежность / касание | collection | When two things are exactly equal or just touch, do they merge, collide, or separate? · Когда два элемента в точности равны или только касаются — они сливаются, сталкиваются или остаются раздельными? |
| empty | Empty / degenerate · пустое / вырожденное | collection, text | What is the result for empty, single-element, or null input? · Каков результат на пустом, одноэлементном или null-входе? |
| encoding | Encoding / representation · кодировка / представление | text | Whose definition of length/equality applies — bytes, code points, grapheme clusters, or normalized form? · Чьё определение длины и равенства действует — байты, кодовые точки, графемные кластеры или нормализованная форма? |
| ordering | Ordering / stability · порядок / устойчивость | collection | When elements compare equal, is output order specified and stable? · Когда элементы равны при сравнении, задан ли порядок вывода и устойчив ли он? |
| precision | Precision / overflow · точность / переполнение | numeric-range | Where can precision loss, overflow, or rounding/tie-breaking occur — and what is the exact contract (e.g. half-up vs half-to-even, ceil/floor/truncate)? · Где возможны потеря точности, переполнение, округление и разрешение «ровно половины» — и каков точный контракт (half-up или half-to-even, ceil/floor/truncate)? |
| idempotency | Idempotency / repetition · идемпотентность / повтор | stateful | What happens if this runs twice on the same input? · Что будет, если выполнить это дважды на одном входе? |
| concurrency | Concurrency / effect ordering · параллельность / порядок эффектов | stateful, io | If interrupted or run in parallel, what is guaranteed? · Что гарантировано при прерывании или параллельном запуске? |

**Фильтр применимости:** категория применима, когда её `applies to shapes`
пересекается с формами требования — «A pure-text requirement is never asked
about overflow» (`edge-probe.md:85-88`). Девятой категории нет: «a fixed eight
the author must explicitly clear beats thirty nobody finishes» (`:64-65`).

Применимой категории задай вопрос таблицы о данных этого требования и ищи один
конкретный край. Нашлось два — бери тот, что тише портит результат. Край, уже
решённый в журнале (Аналитик отказов брейншторма или прежняя проба), второй раз
не поднимается: признак — запись с тем же префиксом `[категория · форма]`,
называющая то же требование; в строке покрытия и в следе идёт её номер
(`spec-phase.md:343`).

### 5. Выбери значение строки

У строки покрытия одно из четырёх значений. Выбирай по порядку, первое подошедшее:

1. Категория не применима к формам требования — `неприменимо: <причина>`.
2. Вопрос задан, конкретного края нет — `не найдено: <что проверялось>`.
3. Край конкретный, но исход уже определён, и ответ человека ничего не изменит —
   `не выбран: <край>; <причина>`.
4. Край конкретный, и от ответа человека зависит, что система сделает на нём —
   `кандидат F-NN`, запись по такту 6.

Сомнение между третьим и четвёртым решается в сторону кандидата: лишнего кандидата
человек отведёт с причиной, а край, ошибочно оставленный `не выбран`, — это отказ
мимо человека.

Разбор на примере:

**`кандидат F-NN`** — край ушёл человеку, в строке номер записи журнала.
Категория `adjacency`: интервалы `[[1,2],[2,3]]` только касаются; сливать ли их
в `[1,3]`, требование не говорит, сценарии тоже, а от ответа зависит число
интервалов в отчёте. Строка — `adjacency · кандидат F-41`. Категория `empty`:
пустой список интервалов; что будет в файле, тоже не сказано. Строка —
`empty · кандидат F-42`. Кандидатом край остаётся и тогда, когда рекомендация
к нему — Dismiss (такт 6).

**`не выбран: <край>; <причина>`** — край найден и не вынесен, записи журнала нет,
край и причина остаются в файле покрытия. Категория `concurrency`: две сборки
одновременно; исход уже назван сценарием «Одна сборка за раз». Строка —
`concurrency · не выбран: две сборки одновременно; исход уже назван сценарием
«Одна сборка за раз», ответ человека его не изменит`. Причина — об этом крае:
«неважно» и «маловероятно» не причины. Каждая такая строка считается в итоге пробы
(такт 10).

**`не найдено: <что проверялось>`** — категория применима, край искали и не нашли;
хвост называет, что проверялось, иначе строку не отличить от «не смотрел». Категория
`ordering`: равные на выходе; интервалы с равным началом пересекаются и сливаются
в один, равных на выходе не остаётся. Строка — `ordering · не найдено: порядок равных
на выходе — интервалы с равным началом сливаются в один, равных не остаётся`. Голое
`не найдено` без хвоста не годится.

**`неприменимо: <причина>`** — формы требования не пересекаются с `applies to shapes`
категории. Вопрос таблицы не задаётся. Категория `boundary`: формы `collection`,
`stateful`, а она только для `numeric-range`. Строка — `boundary · неприменимо: формы
collection, stateful; boundary только для numeric-range`. У применимой категории этого
значения не бывает.

### 6. Запиши кандидата

На каждую строку `кандидат F-NN` — одна запись `decisions.json` по
`journal.schema.json`:

- `kind: развилка`, `status: открыт`, `addressee: человек`,
  `reversibility: null` — кандидат не проектное решение;
- `question` — `[<id категории> · <форма>] <имя требования>: <конкретный край>`:
  префикс — поле формы, которое человек может переписать; край — один, с данными
  этого требования; вопрос таблицы — подсказка модели, не текст записи;
- `evidence[]` — путь spec.md и дословная строка требования
  (`### Requirement: <имя>` или строка с SHALL), чтобы `check` нашёл её;
- `options[]` — ровно четыре; текст варианта — `<Токен> — <текст>`,
  токен (заголовок варианта и первое слово текста) дословно, текст
  конкретен для этого требования и этого края:
  - `A. Specify — <сценарий в одну строку, который появится в spec.md: GIVEN … WHEN … THEN …>; цена: <сценарий, какой тест, сопровождение чего>`
  - `B. Dismiss — <что именно не покрывается и почему это допустимо для этого требования>`
  - `C. Backstop — <какой тест-страховка: что подаёт и что утверждает; строки в spec.md нет>`
  - `D. Defer — <что остаётся открытым и до какого события или решения>`
- **текст варианта не шаблон.** Текст, одинаковый у двух кандидатов
  одного прогона, — дефект кандидата: переписать. Человек выбирает
  по тексту — «что будет при выборе» должно быть видно из него, а не
  из названия исхода;
- `recommendation` — одна, после вариантов, `{option, why, text}`.
  `Specify` рекомендуется, только когда край тихо портит результат или необратим;
  иначе `Dismiss` с причиной. Тихо портит — система выдаёт неверное, и сразу этого
  никто не видит; необратим — порчу не откатить повтором. Такой край формулируется —
  A с черновиком сценария; известен, а в прозу не ложится — C. Остальное — B с готовой
  причиной в `why`. D не рекомендуется. Правило касается только рекомендации: четыре
  варианта есть у каждого кандидата, решает человек;
- `depends_on` — записи, на которых стоит требование;
- `decision: null`, `outcome: null` — их заполнят `apply` и такт 9;
- остальные поля схемы обязательны и пусты: `delivery`, `dispute`, `consequences` —
  `""`; `antipodes`, `parking`, `comments` — `[]`; у варианта `added: false`,
  `unlikely: null`, `evidence: []`.

После каждой записи — `check`, затем `render-md`.

Кандидат на примере:

```text
question: [adjacency · collection] Отчёт сливает интервалы занятости: `[[1,2],[2,3]]` только касаются — сливать в `[1,3]` или оставить два интервала?
A. Specify — GIVEN интервалы `[[1,2],[2,3]]` WHEN собирается отчёт THEN в файле один интервал `[1,3]`; цена: сценарий, тест на касание, правка сценария при смене правила слияния
B. Dismiss — касание не покрывается; допустимо, пока отчёт показывают только суммой часов, а она при обоих ответах одна
C. Backstop — тест подаёт `[[1,2],[2,3]]` и утверждает, что сумма часов в отчёте равна 2 при любом числе интервалов; строки в spec.md нет
D. Defer — правило касания остаётся открытым до решения, считается ли пересменка одним блоком занятости; пока tasks считает, что касающиеся интервалы не сливаются
recommendation: A — в файле то один интервал, то два, и ошибку никто не заметит сразу: отчёт выглядит верным
```

Второй кандидат того же требования, `[empty · collection]`: пустой список интервалов
даёт пустой файл отчёта, человек видит это сразу, и ничего не портится. Рекомендация —
B, причина в `why`; вариант A всё равно есть и называет цену.

### 7. Запиши файл покрытия

Когда все кандидаты в журнале — файл `<каталог изменения>/edge-probe.md`: заголовок
и по строке на пару, в порядке таблицы категорий, требования подряд. Форма строки —
`- <ключ требования> · <id категории> · <значение>`, одна строка файла на пару.
Файл покрытия целиком на примере:

```text
# Покрытие пробы краёв: busy-report-merge

- busy-report/Отчёт сливает интервалы занятости · boundary · неприменимо: формы collection, stateful; boundary только для numeric-range
- busy-report/Отчёт сливает интервалы занятости · adjacency · кандидат F-41
- busy-report/Отчёт сливает интервалы занятости · empty · кандидат F-42
- busy-report/Отчёт сливает интервалы занятости · encoding · неприменимо: формы collection, stateful; encoding только для text
- busy-report/Отчёт сливает интервалы занятости · ordering · не найдено: порядок равных на выходе — интервалы с равным началом сливаются в один, равных не остаётся
- busy-report/Отчёт сливает интервалы занятости · precision · неприменимо: формы collection, stateful; precision только для numeric-range
- busy-report/Отчёт сливает интервалы занятости · idempotency · не найдено: вторая сборка на тех же интервалах — итог зависит только от входа, файл перезаписывается тем же содержимым
- busy-report/Отчёт сливает интервалы занятости · concurrency · не выбран: две сборки одновременно; исход уже назван сценарием «Одна сборка за раз», ответ человека его не изменит
```

Перед закрытием сверь счёт: строк в файле ровно восемь на требование. `check` этот файл
не разбирает и о пропуске не скажет.

### 8. Круг просмотрщика

Когда кандидаты по всем требованиям записаны — `render-html`, назови
человеку путь к `decisions.html`. Человек выбирает исход и пишет слово:
у B слово — причина; у A — строка критерия, если он задаёт её сам.
Промпт возврата сохрани в `<каталог изменения>/answers/<дата>.md` (дата `YYYY-MM-DD`; файл занят — `YYYY-MM-DD-2.md`, затем `-3`) как
есть и внеси `apply`; отказ называет запись — исправь строку промпта,
не JSON. «Реши сам» — тоже слово человека: внеси рекомендованный
вариант строкой `- F-NN: X — «реши сам»`, букву не подменяй. У
рекомендованного B причиной становится `why` рекомендации с пометкой
«по слову „реши сам“» — отказа без причины нет (`spec-phase.md:370-371`
«never auto-dismiss — a wrong dismissal is the exact silent failure
being eliminated»: причина есть, и она видна в журнале).

### 9. Зеркало исхода

После `apply` у каждой записи пробы с `decision`:

- `outcome` ← `{kind: "проба", value: <слово варианта: A → Specify,
  B → Dismiss, C → Backstop, D → Defer>, reason: <decision.word дословно;
  у B по «реши сам» — `why` рекомендации с пометкой>}`;
- A: в spec.md под требованием — новый `#### Scenario:` с GIVEN/WHEN/THEN
  на этот край (грамматика OpenSpec: критерий приёмки — сценарий), после
  последнего сценария и выше строк следа; слово человека к A — основа
  сценария, смысл не меняй; `consequences` ← «в spec.md: <имя сценария>»;
- C: `consequences` ← «тест-страховка: <что проверяет>»; тест пишет
  `tasks`, здесь только намерение;
- D: `consequences` ← «край не решён — tasks считает его допущением»
  (`spec-phase.md:364-365`);
- B: `consequences` ← причина; spec.md не меняется.

**B без слова.** `outcome` такой записи не пиши: без причины `check`
покрасит её «исход Dismiss без причины», и на негодном журнале `apply`
откажет даже верной строке. Причину не выдумывай: спроси человека в чате,
внеси строкой `- F-NN: к решению B — «причина»` через `apply` и только потом
зеркаль запись. `outcome` уже записан — верни его в `null` и повтори.

### 10. След в spec.md и итог

След стоит в конце блока каждого требования, после всех его сценариев: выше первого
сценария он считается в предел 500 символов текста требования, и `validate --strict`
падает на длинном следе. Заполни комментарий шаблона
(`openspec/schemas/symphysis/templates/spec.md:15`):
`<!-- проба краёв: форма=<формы>, исходы: F-NN Specify, F-MM Dismiss, … -->`;
кандидат без решения пишется как `F-NN открыт`, кандидатов нет — `исходы: нет`.

Закрой пробу строкой `notes[]`: `{date, text: «проба краёв: кандидатов N, Specify a,
Dismiss b, Backstop c, Defer d; не выбран k: <ключи требований через запятую>»}`.
`k` — число строк `не выбран` в файле покрытия, дальше ключи их требований, у `k = 0` —
`не выбран 0`. Без этого счёта такой край был бы отказом, которого человек не видит:
строка итога — единственное, что выводит его наружу. Кандидаты без решения входят в N
и перечисляются номерами. Затем `render-md`, `render-html`. Открытый кандидат артефакт
не блокирует: его увидят атака `symphysis-attack` и Open Questions дизайна.

### 11. Выключенная проба

Такт идёт вместо всех прочих, когда состав назвал `проба краёв выкл`.

**Файла покрытия нет и кандидатов пробы в журнале нет.** Кандидатов не заводи, файл
покрытия не пиши. В конец блока каждого требования поставь
`<!-- проба краёв: выключена настройкой -->`. Комментарий нужен, чтобы выключенная
проба не читалась как пройденная. Проба запретов идёт независимо: её этот такт не касается.

**Прежний проход уже был** (файл покрытия или записи `[<категория> · <форма>]`). Файл
и записи остаются как есть: они несут слово человека. Новых записей нет. След называет
выключение рядом с прежними номерами:
`<!-- проба краёв: выключена настройкой; прежний проход: форма=<формы>, исходы: F-NN Specify, … -->`.

## Повтор пробы

Проба идёт снова после правки или переименования требования.

- Файл покрытия переписывается целиком: старые строки не переносятся, строк про требования,
  которых больше нет, в нём нет.
- Кандидат сохраняет номер и решение: запись ищи по категории и требованию, у переименованного —
  по новому имени; в строке покрытия её номер, второй записи нет. Имя требования
  в `question` и `evidence[].quote` поправь на новое, иначе `check` даст «цитаты нет дословно»;
  `decision` и `outcome` не трогай. Префикс, переписанный человеком, не возвращай.
- Снятое требование строк не получает, его запись остаётся в журнале.
- След и строка итога пишутся заново по новому файлу.

## Чего скилл не делает

- не ставит исход сам: `decision` — только из `apply`, `outcome` — зеркало
  слова человека, не оценка модели;
- не принимает Dismiss без причины и не сочиняет причину за человека;
- не спрашивает человека о составе, не читает и не правит `symphysis.yaml`;
- не переводит требование и не ищет cue-слова: форму называет модель
  по смыслу, человек правит;
- не добавляет категорий и не поднимает `unclassified`;
- не оценивает обратимость: кандидат — не проектное решение;
- не пишет тест страховки — только намерение в `consequences`;
- не спрашивает «чем это станет молча» — `symphysis-prohibition-probe`.

## Приёмка

| Проверка | Чем держится |
| --- | --- |
| решает человек | `decision` только из `apply`; `outcome.value` совпадает с буквой решения, `reason` — слово дословно (у B по «реши сам» — `why` рекомендации с пометкой) |
| отказ с причиной | `check` зелёный: ни одного Dismiss с пустой причиной; причина — слово человека, не модели |
| покрытие полное | в `edge-probe.md` восемь строк на каждое требование ADDED и MODIFIED, ключ `<capability>/<имя>`; значение из четырёх; у `не найдено` хвост, у `не выбран` край и причина |
| край конкретный | `question` называет данные этого требования; вопрос таблицы дословно в `question` не встречается |
| тексты вариантов конкретны | каждый текст начинается своим токеном (Specify, Dismiss, Backstop, Defer); четыре текста попарно различны и не повторяют текст другого кандидата прогона |
| рекомендация по правилу | A или C только у края, который тихо портит результат или необратим, с этим в `why`; вариант A называет цену |
| фильтр соблюдён | у каждого кандидата категория из восьми и форма из пяти; категория применима к форме по таблице |
| форма правится человеком | префикс `[id · форма]` в `question`; переписанный человеком префикс моделью не возвращается |
| след в spec.md | у каждого требования комментарий «проба краёв» в конце блока, после сценариев, с формой и исходами по номерам; на каждый Specify — сценарий |
| проба закрыта счётом | строка `notes[]` с N, a, b, c, d, числом строк `не выбран` с ключами требований и датой |
| выключенная проба | кандидатов и файла нет, след `выключена настройкой` у каждого требования; прежний проход не тронут |
