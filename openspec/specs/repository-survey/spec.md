# repository-survey Specification

## Purpose
Обследование исходных репозиториев изменения моделью: переносимый состав, состояния анализа, локальные корни и бережное обновление metadata в существующих шагах.

## Requirements

### Requirement: Обследование репозиториев начинается в decisions
При чтении материалов intent шаг decisions SHALL назвать участвующие репозитории, обследовать доступные объявления модулей и сообщить результат. Research SHALL уточнять недоступное и вновь найденные репозитории. Новый обязательный шаг конвейера не вводится; повтор обследования нужен при изменении состава или объявлений (trace-modules/F-26, trace-modules/F-29).

#### Scenario: Первое обследование по intent
- **GIVEN** intent называет два исходных репозитория
- **WHEN** модель выполняет decisions
- **THEN** состав репозиториев и результат обследования каждого отражены в metadata изменения и сообщены человеку

#### Scenario: Репозиторий найден исследованием
- **GIVEN** research выявил ещё один затронутый репозиторий
- **WHEN** модель уточняет состав изменения
- **THEN** новый репозиторий обследован, результат добавлен без повторного создания прежних записей

### Requirement: Состав компонентов и репозиториев хранится переносимо
Состав SHALL храниться в x-symphysis-components файла .openspec.yaml: компонент содержит явно названные repo. Компонент и репозиторий SHALL оставаться разными уровнями; один компонент может содержать несколько repo. Локальный абсолютный каталог в эти объявления не входит. Поле commit, если задано, означает снятое состояние, а не текущее содержимое рабочей копии (trace-modules/F-17).

#### Scenario: Два репозитория одного компонента
- **GIVEN** один компонент реализован в двух repo
- **WHEN** состав записан в metadata
- **THEN** сохраняются один компонент и две самостоятельные записи repo

#### Scenario: Коммит не подменяет рабочие файлы
- **GIVEN** repo имеет commit и незакоммиченную правку README
- **WHEN** строится живой граф
- **THEN** объявление читается из рабочей копии; commit не выдаётся за содержимое прочитанного README

### Requirement: Результат обследования различает четыре состояния
Запись repo SHALL различать: модули обнаружены, модулей нет, репозиторий недоступен, ещё не обследован. Отсутствие metadata MUST NOT считаться доказанным отсутствием модулей. При результате «модулей нет» граф SHALL не создавать вымышленные модули и их связи; остальные доступные артефакты продолжают образовывать граф (trace-modules/F-21, trace-modules/F-26, trace-modules/F-30).

#### Scenario: Обследованный репозиторий без модулей
- **GIVEN** доступное дерево обследовано и объявлений модулей нет
- **WHEN** собирается граф
- **THEN** результат означает отсутствие объявленных модулей; узлов и связей модулей нет, требования и задачи остаются

#### Scenario: Клон недоступен
- **GIVEN** объявленный repo отсутствует по своему локальному корню
- **WHEN** обследуется состав
- **THEN** результат означает недоступность, а не отсутствие модулей

#### Scenario: Обследование ещё не записано
- **GIVEN** у repo нет результата обследования либо metadata отсутствует
- **WHEN** собирается отчёт
- **THEN** отсутствие анализа отличимо от подтверждённого результата «модулей нет»

#### Scenario: Одно негодное объявление не доказывает отсутствие модулей
<!-- trace-modules/F-39 -->
- **GIVEN** доступное дерево содержит единственное явное объявление README с kind: служебный и не содержит валидных модулей
- **WHEN** модель завершает попытку обследования
- **THEN** результат не объявляется «модулей нет»: обследование остаётся незавершённым, со состоянием «ещё не обследован» и сигналом негодного объявления

### Requirement: Repo разрешается через явно названный корень
Каждый repo SHALL связываться с явно названным псевдонимом существующей карты корней; пустой префикс может обозначать текущий проект. Команды графа SHALL использовать один resolver и принимать явный файл --roots. Наличие префикса в карте само по себе MUST NOT объявлять репозиторий участником изменения (trace-modules/F-17, trace-modules/F-31).

#### Scenario: Текущий и внешний репозитории
- **GIVEN** состав называет repo с пустым префиксом и repo с внешним псевдонимом
- **WHEN** команды читают одну явно переданную карту
- **THEN** каждый repo разрешён своим псевдонимом; его логическое имя не заменено каталогом клона

#### Scenario: Посторонний префикс улик
- **GIVEN** карта содержит дополнительный префикс, которого нет в составе
- **WHEN** строится граф
- **THEN** этот префикс не создаёт ещё один repo и не расширяет обследование

#### Scenario: Неизвестный псевдоним не подменяется пустым префиксом
<!-- trace-modules/F-48 -->
- **GIVEN** repo называет отсутствующий псевдоним, карта содержит пустой префикс и в текущем проекте есть одноимённый подкаталог
- **WHEN** сборщик разрешает корень repo
- **THEN** источник назван недоступным с причиной отсутствия псевдонима; подкаталог текущего проекта не обследован вместо него, другие доступные repo сохранены

### Requirement: Структурные источники остаются внутри разрешённого корня
Пути объявлений, исключений и файлов реализации SHALL разрешаться внутри явно выбранного корня repo после нормализации разделителей и разрешения ссылок. Выход за корень через относительный переход, абсолютный хвост, symlink или junction MUST NOT приводить к чтению внешнего файла. Отказ даёт сигнал с логическим местом и причиной; остальные доступные источники сохраняются. Повторное посещение каталога по ссылке MUST NOT делать обход бесконечным (trace-modules/F-46).

#### Scenario: Обход границы через путь или ссылку
- **GIVEN** путь объявления или реализации содержит ../, абсолютный хвост либо symlink/junction с целью вне разрешённого корня
- **WHEN** источник разрешается для обследования или графа
- **THEN** внешний файл не читается, сигнал называет логический источник и причину; корректные модули других источников сохранены

#### Scenario: Цикл каталогов через ссылку
- **GIVEN** ссылка внутри разрешённого repo возвращает обход в уже посещённый каталог
- **WHEN** обнаруживаются README модулей
- **THEN** обход завершается и не создаёт дубликаты модулей из повторного посещения

### Requirement: Модель изменяет только своё расширение metadata
Модель SHALL точечно обновлять x-symphysis-components средствами редактирования файлов и проверять итоговый diff. Остальные данные .openspec.yaml SHALL сохраняться. Writer создания metadata OpenSpec MUST NOT применяться к прочитанному объекту для такого обновления; отдельная операция записи в CLI не требуется (trace-modules/F-36).

#### Scenario: Сохранение посторонних данных
- **GIVEN** metadata содержит schema, created и чужое расширение
- **WHEN** модель записывает результат обследования своего расширения
- **THEN** все посторонние данные сохраняют значения; diff содержит только необходимое изменение своего расширения

#### Scenario: Состав metadata изменился после чтения
<!-- trace-modules/F-38 -->
- **GIVEN** metadata прочитан моделью, затем другой участник добавил repo в то же расширение
- **WHEN** модель собирается сохранить результат прежнего чтения
- **THEN** модель перечитывает и сохраняет новые данные либо отказывается затирать их до повторного анализа

### Requirement: Новое чтение не заменяется прежним результатом обследования
Живой граф SHALL читать текущие объявления README без дублирующего сохранённого списка модулей. Если новое чтение расходится с результатом обследования repo, отчёт SHALL назвать расхождение для уточнения анализа. Сборщик MUST NOT сам изменять записанный моделью результат или скрывать обнаруженный модуль только из-за прежнего «модулей нет» (trace-modules/F-16, trace-modules/F-30).

#### Scenario: Модуль появился после обследования
- **GIVEN** результат repo — «модулей нет», затем появился валидный README модуля
- **WHEN** граф собран снова
- **THEN** модуль присутствует в живой структуре, расхождение показано сигналом; metadata не переписан сборщиком

#### Scenario: Повтор без изменений
- **GIVEN** состав и объявления после обследования не менялись
- **WHEN** анализ повторён
- **THEN** не создаются дубликаты repo и модулей
