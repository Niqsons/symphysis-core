# Security

| Пункт | Применимо / неприменимо — причина | Чем проверено |
| --- | --- | --- |
| Инъекции через содержимое файлов | применимо — требования `record-anchors` «Голые номера блока переписываются в мастере при синхронизации» и `trace-graph` «Скрипт сам разбирает спеки с номерами строк»: скрипт и граф читают дельты, мастер-спеки и базу снимка; текст спек, HTML-комментарии и строки базы — данные, разбор идёт регулярками без исполнения, скрипт заменяет только токены, которые граф читает как ссылки, и пишет файл целиком тем же способом, что снимок графа (парковка F-55) | тесты разбора ссылок и переписывания на фикстурах (задачи `tasks`); сценарии «Образец в обратных кавычках», «След проб после последнего сценария», «Ссылка с именем не трогается» |
| Пути с `../` | применимо — требования `record-anchors` «Голые номера блока переписываются в мастере при синхронизации» и «Скрипт не трогает файлы изменения»: единственный путь записи — `openspec/specs/<capability>/spec.md` под корнем проекта, capability берётся из имени каталога дельты; имя с `..`, абсолютный путь или ссылка за корень — отказ до записи (парковка F-55) | тест на имя capability, выводящее за корень (задача `tasks`); сценарии «Каталог изменения прежний», «Номер вне журнала и чужой блок» |
| Токены и срок их жизни | неприменимо — изменение не вводит токенов, ключей, сети и учётных данных; `openspec validate` форк запускает, как прежде, через общий модуль запуска | чтение `proposal.md` и `specs/`: ни одно требование не называет токен, ключ или сеть |
| Права | применимо — требования `record-anchors` «Скрипт не трогает файлы изменения», «Переписывание зовётся правилом синхронизации» и «CLI-архив не применяется к мастеру с якорями»: появляется новый писатель мастер-спек — скрипт по вызову модели; до изменения мастер правила только модель скиллом sync (F-30); каталог изменения, журнал и снимок скрипт только читает, архив остаётся за скиллом | сценарий «Каталог изменения прежний» — тест хешей каталога изменения после запуска; `git diff` синхронизации против вывода скрипта при показе (сценарий «Дифф совпадает с выводом скрипта») |
| Бинарные файлы | неприменимо — граф и скрипт читают только `spec.md`, `decisions.json` и `req-graph.json` как UTF-8; файл не UTF-8 даёт отказ с именем файла, как у графа сегодня (`trace-graph`, тест `test_spec_not_utf8_names_the_file`), скрипт переписывания берёт тот же читатель | тест графа на не-UTF-8; тот же тест для скрипта (задача `tasks`) |
| Чувствительные данные в журнале, артефактах и журналах прогона | применимо — требование `record-anchors` «Ссылка на запись несёт якорь изменения»: якорь несёт имя изменения в мастер-спеку, снимок и вывод скрипта; имена изменений уже стоят в репозитории; `report.md` по-прежнему без абсолютных путей; следы проб исследования `research/F-21-probe/`, `research/F-24-probe/` несут только временные пути без имени машины и рабочих имён | гейт имён `check_names.py` хуком на каждом коммите изменения; чтение `research/` и `briefs/` при коммите |
| Имя изменения как аргумент скрипта | применимо — требования `record-anchors` «Переписывание зовётся правилом синхронизации» и `trace-conventions` «Несуществующее имя изменения не чужой журнал»: имя приходит из команды правила и из текста спек (якорь); проверка имени тем же правилом, что `check_change_name` графа — символы оболочки, пустое имя, ведущий дефис дают отказ до любого пути; имена изменений для сверки читаются из каталогов `openspec/changes/` и архива, а не строятся из текста как путь (парковка F-56) | тест `test_bad_change_name_is_refused_before_any_path` графа и такой же для скрипта (задача `tasks`); сценарий «Опечатка в имени изменения» |
