## ADDED Requirements

### Requirement: Контракт ядра предоставляет единое разрешение поставки для хостов
Ядро SHALL предоставлять хостам тот же resolver runtime и ресурсов, что dispatcher symphysis. В режиме local результат SHALL указывать проектную поставку, в режиме global — активную пользовательскую; при наличии обеих resolver SHALL выбирать local. Контракт SHALL NOT требовать от хоста собственного алгоритма выбора поставки (F-10, F-13).

#### Scenario: Хост и dispatcher выбирают одну поставку
- **GIVEN** store без локальной установки и совместимая активная global-поставка
- **WHEN** хост разрешает инструменты и ресурсы через контракт ядра, а dispatcher запускается для того же store
- **THEN** обе стороны получают одну поставку; каталог общего runtime не становится корнем store

#### Scenario: Локальная поставка важнее пользовательской
- **GIVEN** в store есть local-поставка, у пользователя также есть global-поставка
- **WHEN** хост обращается к resolver ядра для этого store
- **THEN** resolver выбирает local; этот выбор не обещает исправления конфликтов нативной discovery скиллов и агентов клиента

### Requirement: Разрешение runtime не меняет рабочий store вызовов хоста
Контракт вызова инструментов SHALL разделять выбранный runtime и рабочий store. Расчёт справки, чтение журнала, `apply` и пересборка производных SHALL сохранять рабочий корень выбранного store независимо от расположения исполняемого кода. Проектные пути SHALL NOT разрешаться относительно каталога пользовательской поставки (F-10).

#### Scenario: Два store используют общий runtime
- **GIVEN** два store с изменениями одинакового имени и одна совместимая global-поставка
- **WHEN** хост запрашивает журнал и справку для каждого store
- **THEN** каждый ответ относится к выбранному store, а не к каталогу runtime или одноимённому изменению другого store

#### Scenario: Ответ человека остаётся в выбранном store
- **GIVEN** host работает с global runtime и журналом выбранного store
- **WHEN** пользователь вносит слово через существующий `apply` и пересобирает производные
- **THEN** журнал, файл ответа и производные принадлежат выбранному store; данные другого store и runtime не изменены этим внесением

### Requirement: Контракт разрешения сообщает несовместимость выбранной поставки
Если выбранная поставка несовместима со store, ядро SHALL возвращать хосту явную причину отказа и необходимое действие, не выдавая несовместимость за отсутствие журнала или пустой список изменений. Неуспешное разрешение SHALL NOT менять данные store, выполнять миграцию или подставлять другую поставку для продолжения операции (F-10, F-11, F-13).

#### Scenario: Обновлённый global runtime несовместим со store
- **GIVEN** активная global-поставка обновлена, а выбранный store несовместим с ней
- **WHEN** хост обращается к контракту разрешения для операции над этим store
- **THEN** ответ называет несовместимость и необходимое действие; операция не продолжена на другой поставке, файлы store не изменены

### Requirement: Контракт сохраняет проектную принадлежность черновиков
Глобальное расположение runtime SHALL NOT переносить черновики, ответы, события и курсоры из выбранного store в общий пользовательский runtime. Контракт ядра SHALL сохранять различение состояния разных store, включая одноимённые изменения. Подключение новой global-поставки SHALL NOT очищать проектные черновики (F-03, F-10, F-11).

#### Scenario: Обновление общей поставки сохраняет два черновика
- **GIVEN** в двух store есть разные черновики одноимённых изменений и используется global-поставка
- **WHEN** активная поставка совместимо обновлена и хост снова разрешает каждый store
- **THEN** оба черновика остаются в своих store байт в байт; общий runtime не становится их хранилищем
