# Пробы описи последствий

Дата: 2026-11-08. Исходники ядра — worktree `feat/global-user-install`, HEAD `6189f15`; форк OpenSpec — `cf45eb2a`, версия `1.16.1+symphysis.5`. Исходники только читались. Пробы запускаются файлом `consequences-probe.py`; результат — `consequences-results.json`.

Все фикстуры, временные конфиги и данные созданы внутри `X:/codex-tmp/global-consequences-probe`. Личные конфиги, карты корней и реестры store не читались; нативные клиенты и модели не запускались. Fork CLI запускался напрямую из локального `upstream`, без сборки и изменения его файлов.

1. **Карта корней при внешнем runtime.** В фикстуре store есть собственная карта с пустым префиксом `<root>/..` и префиксом `src/`. `default_roots(journal_path=...)` из внешней копии runtime возвращает только корень store и теряет `src/`. Передача этой карты через `roots_file` возвращает `src/`, но раскрывает `<root>/..` от runtime, а не от проектной `.symphysis`. Это поведение существующего кода, не готовое решение global-установки.
2. **Несколько клиентов.** У первого каталога клиента есть `openspec-continue-change`, у второго есть другой workflow, но нет continue. `selectedClients` различает наличие continue; `continueLines` всё равно возвращает пустые findings, а `ensureContinue` сразу возвращает пустой результат. Полнота workflow второго выбранного клиента этим не подтверждается. Discovery скиллов самим клиентом здесь не проверялось.
3. **Ресурс на другом диске.** Стандартный `ntpath.relpath` для путей на разных дисках бросает `ValueError`. При искусственной подстановке такой ошибки в `_relative_link` результат — `None`: ссылка исключается. Физическая раскладка на двух дисках и браузер в этой пробе не проверялись; все созданные файлы остаются на X.
4. **Нативная схема OpenSpec.** Документация `upstream/openspec/docs/opsx.md:591–595` описывает `schema which` и проектное/пользовательское размещение. В запуске `schema which symphysis --json` проектная схема выбирается раньше пользовательской и сообщает `shadows`; без проектной выбирается пользовательская. Это согласуется с `getSchemaDir` в `resolver.ts:163–175`. Наличие локальной схемы само по себе ещё не доказывает наличие полноценной local-установки symphysis.
5. **Нативное создание изменения.** В отдельной фикстуре без декларации совместимости symphysis вызов `openspec new change native-no-declaration` завершился кодом 0 и создал каталог изменения. Шаблон workflow `new-change.ts:63` вызывает эту нативную команду. Проба показывает необходимость согласовать документированный клиентский путь с F-15; она не утверждает, что нынешний OpenSpec обязан знать ещё не реализованный контракт совместимости symphysis, и не подтверждает поведение модели в сессии.

6. **Неверная структура planning config.** `mergeConfig` получил `rules` и `operations` как строки. Значение `rules` заменено собственной map без предупреждения о потере этой строки; `operations` сохранён, но подсказки не добавлены и возвращено предупреждение. Полноценный install не запускался: проверялось чистое слияние переданных строк.

Пробы фиксируют существующие ветки и основу кандидатов описи. Они не являются приёмкой global-установки и не заменяют проверку установленных клиентских интеграций.
