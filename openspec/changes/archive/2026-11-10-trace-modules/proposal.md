# Proposal

## Why

После `trace-graph` и `module-structure` репозиторий symphysis имеет объявления модулей, но req graph их не использует (F-09–F-13, F-27). Изменение добавляет ось «где код» и связывает её с требованиями; готовность проверяется на настоящих модулях symphysis и межрепозиторной фикстуре (F-01–F-07, F-25).

Это функциональность для любых репозиториев с явно обозначенными модулями. Собственный репозиторий — пример для проверки; его раскладка не задаёт расположение модулей клиента (F-16, F-18, F-32, уточнение владельца в F-35).

## What Changes

- В существующие шаги `decisions` и `research` входит обследование участвующих репозиториев: состав, доступность и результат обнаружения модулей. Результат различает обнаруженные модули, их отсутствие, недоступность репозитория и ещё не выполненное обследование (F-26, F-29, F-30).
- Переносимые объявления компонентов и репозиториев и результат обследования хранятся в `x-symphysis-components` изменения. Локальный каталог разрешается по явно названному псевдониму существующей карты корней. Модель точечно обновляет своё расширение, сохраняя остальные данные metadata (F-17, F-31, F-36).
- Объявления README читаются в рабочем дереве на любой глубине, включая корень, без обязательного Git и с переносимыми исключениями. Все объявленные модули участвующих репозиториев попадают в структуру; файловые узлы ограничены файлами, которые участвуют в трассировке. Принадлежность файла задаёт ближайшая граница модуля (F-16, F-18, F-32, F-33).
- Граф получает узлы компонентов, репозиториев, модулей и файлов, структурные связи и связи реализации «многие ко многим». Требование явно называет модули и при необходимости файлы аннотацией в своём блоке; зависимости модулей берутся из деклараций README. Идентичность требования не включает модуль, а улика о коде не становится подтверждённой связью реализации автоматически (F-14, F-19, F-20, F-34, F-35).
- Недоступность, неоднозначные объявления и расхождение сохранённого результата обследования с новым чтением видны сигналами. Корректная часть графа сохраняется; отсутствие модулей не подменяется недоступностью или отсутствием анализа (F-21, F-26, F-30).
- Формат JSON графа получает новую версию (**BREAKING**). Снимок сохраняет нормализованную структуру, состояния, происхождение связей, состав объявлений и их хеши. Предыдущий поддерживаемый формат 2 читается без обещания структурных сведений; архивы автоматически не переписываются (F-22, F-23, F-27, F-37).
- Текстовый экспорт `requirementDiagram` и существующие фильтры включают связанную структуру с необходимыми предками. Концептуальная `scheme.md` сохраняет своё назначение; рендер requirementDiagram в плагине остаётся отдельным изменением (F-24).
- `GUIDE.md` описывает обозначение модулей и зависимостей, обследование, источники связей, ограничения и сигналы. README сторонних репозиториев продукт автоматически не изменяет; применение соглашения к собственным модулям symphysis служит проверкой результата (F-07, F-25, F-35).

## Capabilities

Обследование моделью и детерминированное обнаружение модулей разделены по смыслу: момент и состояние обследования можно менять независимо от правил чтения README (F-18, F-29, F-30, F-32).

### New Capabilities

- `repository-survey`: обследование репозиториев в существующих шагах, переносимый состав компонентов/repo, состояния обследования, привязка к локальным корням и точечное обновление metadata (F-17, F-26, F-29–F-31, F-36).
- `module-discovery`: чтение явных объявлений модулей и зависимостей из README на произвольной глубине, исключения обхода, границы модулей и принадлежность используемых файлов; сторонние README остаются входными данными (F-18, F-20, F-32, F-33, F-35).

### Modified Capabilities

- `trace-graph`: источники и состав графа расширяются структурной осью и явными связями реализации; дополняются идентификаторы, версия формата и проверка сохранённого графа (F-14, F-16, F-19, F-23, F-33, F-34).
- `trace-conventions`: добавляется соглашение об аннотации реализации в блоке требования и её сохранении при синхронизации; связь не выводится из одного упоминания файла (F-19, F-34).
- `trace-snapshot`: заморозка и проверка учитывают нормализованные структурные объявления, их состав и хеши, состояния источников и поддержку прежнего формата 2 (F-22, F-23, F-37).
- `trace-signals`: закрытый состав отчёта дополняется сигналами обследования и структурных связей с сохранением доступной части графа и сигнального характера проверок (F-21, F-30).
- `trace-diagram`: структурные виды и связи входят в конфигурацию текстового экспорта и фильтры требования/capability; экспорт остаётся текстовым (F-24, F-33).

## Impact

- Ядро: `trace/`, разрешение корней в `roots/`, источники `.openspec.yaml`, дельты требований и README модулей, JSON графа и снимка, отчёт и экспорт Mermaid (F-13, F-17, F-21–F-24, F-31, F-34–F-37).
- Процесс: instruction существующих шагов, скиллы брейншторма и исследования, соглашения написания требований и `docs/GUIDE.md`. Новый обязательный шаг конвейера, отдельная операция записи metadata в CLI и выпуск форка для неё не требуются (F-29, F-34–F-36).
- Поставка и проверки: установленная копия должна содержать реализацию чтения модулей; затрагиваются её списки файлов и тестовые стенды. Проверка на собственных модулях включает сборку, сигналы, freeze/check и отфильтрованный экспорт; фикстура различает одноимённые модули разных репозиториев (F-01, F-13, F-25, F-27, F-28).
- Данные клиента: соглашения документируются для владельца репозитория; автоматическая правка его README не входит в операции продукта. Для снимка сохраняются нормализованные объявления, а не копии исходного кода и полные тексты README (F-35, F-37).
