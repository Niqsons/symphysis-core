# F-26 · Как текущий форк хранит расширения metadata изменения и как продукт может разрешить объявленные репозитории и модули?

## Найдено

1. Metadata: расширение хранится в YAML, но не в типизированном результате чтения. Проверены CLI и публичный helper уже собранного форка; новая сборка не делалась.

- `upstream/openspec/docs/cli.md:721` «**Keep your own metadata:** a top-level key starting with a lowercase `x-` is»: документирован верхнеуровневый ключ с префиксом `x-`; продолжение документации ограничивает префикс нижним регистром, непустым именем без пробелов и запрещает расширения внутри `initiative`.
- `upstream/openspec/src/utils/change-metadata.ts:26` «export const EXTENSION_KEY_PATTERN = /^x-\S+$/;»: `x-symphysis-components` отвечает текущей форме ключа; вложенное содержимое этого расширения OpenSpec не типизирует.
- `upstream/openspec/src/utils/change-metadata.ts:138` «* keys back from the raw YAML first or it silently deletes them.»: writer предназначен для нового файла; при перезаписи требуется вернуть неизвестные ключи из сырого YAML, иначе они теряются.
- `upstream/openspec/src/utils/change-utils.ts:167` «throw new Error(`Change '${name}' already exists at ${changeDir}`);»: `new` не дописывает metadata в существующий change; новый файл создаёт writer с известными полями.
- `openspec/changes/trace-modules/research/F-26-probe/summary.txt:4` «new creates only known metadata; repeated new refuses; status/instructions(json,text)/strict validation/archive preserve exact metadata bytes»: `new` создал обычный metadata без расширения; после добавления вложенного components повторный new отказал, status, обе формы instructions, strict validation и archive оставили все байты metadata прежними.
- `openspec/changes/trace-modules/research/F-26-probe/summary.txt:5` «extensionAfterRewrite\":false»: helper вернул только schema/created/skip_specs, неизвестных предупреждаемых ключей не было; запись прочитанного объекта в том же временном файле удалила расширение.

2а. Имена и пути: старый разбор описывает проект расширения, а текущий читатель настроек такой карты не принимает. Корни улик разрешают пути, а снимок графа хранит префикс и HEAD, без имени компонента.

- `docs/analysis/stores-and-context-pack-2026-11-02.md:159` «**Найдено: личная карта.** Имя и путь: `repos:` в `symphysis.yaml`, он личный, вне git, и читатель у него уже есть (`symphysis_config.py`). Раньше я предлагал `journal-roots.json`, но он лежит рядом с инструментами и отвечает за улики. При `-g` карта уходит на уровень машины (раздел 5). Адрес для клонирования коллегой можно добавить позже, ключом в `openspec/config.yaml` хранилища: тогда сигнал даст готовую команду.»: в разборе предложен `repos:`; это описание замысла, проверка ниже показывает расхождение с текущим кодом.
- `settings/symphysis_config.py:87` «settings.signals.append(f"{FILE_NAME}: неизвестный ключ {group}")»: неизвестная группа настроек даёт сигнал, а не регистрацию репозитория; в KEYS есть consequences, edge_probe, drivers, attack.
- `openspec/changes/trace-modules/research/F-26-probe/summary.txt:11` «symphysis.yaml: неизвестный ключ repos»: синтетический repos отклонён `_apply`; полный read_settings в python -I упёрся в отсутствующий PyYAML, поэтому это проверка классификации уже разобранной карты, а не успешного YAML-чтения.
- `roots/roots.py:71` «"""Префикс пути улики -> каталог — только из файла корней (`tools/journal-roots.json`»: действующая карта относится к префиксам улик и каталогам; личный файл карты не читался.
- `roots/roots.py:107` «"""Файл улики по самому длинному подходящему префиксу: `None` — корня для пути нет,»: вложенный путь разрешается по самому длинному префиксу с защитой от выхода за корень; проба с явной обезличенной картой работает без Git.
- `trace/trace_graph.py:1701` «# Снимок `graph/req-graph.json`: поля графа и `roots`, `base`. `roots` — `[{"prefix", "commit"}]` по файлу корней, в его порядке;»: текущая фиксация происхождения — prefix/commit корней улик; это не объявление модулей или многоуровневый components/repo intake.

2б. Store существует в OpenSpec как дом планирования с собственной регистрацией; это отдельная механика от заявленной карты исходных репозиториев.

- `upstream/openspec/src/core/store/foundation.ts:39` «local_path: string;»: у backend записи store есть локальный путь; рядом определены тип git, необязательные remote/branch и реестр version/stores.
- `upstream/openspec/docs/agent-contract.md:61` «OpenSpec does not route a store's tasks to repos, so the declaring project is the current one, not every repo the change touches.»: контракт прямо ограничивает store: задачи по исходным репозиториям он не маршрутизирует.
- `openspec/changes/trace-modules/research/F-26-probe/summary.txt:6` «setup --no-init-git and declared store pointer new/status succeed; no .git exists»: в изолированном global data создан store без Git; `store:` указатель привёл new/status к root.source=declared, .git не появился.
- `installer/lib/install.js:75` «/** Короткий хеш HEAD клона или null: нет git, нет репозитория или каталог лежит внутри чужого репозитория. */»: инсталлятор знает HEAD собственного клона для версии установки; это не снимок исходного repo, названного компонентом.

3. Проверка структуры — гейт самого ядра, с привязкой к Git и формату README. Она обнаруживает часть вложенных модулей именно для сообщения о запрещённом размещении.

- `tests/repository_structure.py:137` «found = {d for d, m in marks.items() if m == "модуль" and d in repo.dirs}»: модуль первого уровня берётся по пометке «модуль» в README корня; далее отдельно добавляется константа openspec/schemas/symphysis и вложенные README с frontmatter.
- `tests/repository_structure.py:230` «"""1.4: модуль — каталог первого уровня или `openspec/schemas/symphysis`; модуль в модуле — красный."""»: вложенная схема — специальное исключение; любой другой модуль на глубине получает замечание, как и модуль внутри модуля.
- `openspec/changes/trace-modules/research/F-26-probe/summary.txt:8` «"found": ["openspec/schemas/symphysis", "src/deep/marked", "top"]»: на обезличенной структуре найдены top, src/deep/marked и специально зашитая схема; src/deep/marked запрещён по месту. ## Вопросы, которые открылись

- Какой контракт переносит логическое имя объявленного repo в локальный корень исследования: корни улик уже работают, `repos:` из старого разбора текущим читателем не принят? Источники: stores-and-context-pack, settings, roots; конструкция здесь не выбрана.

- Какой вход получает анализатор исходников, если planning root — store и затронуты несколько repo, а OpenSpec сам задачи по repo не маршрутизирует? Источник: agent-contract.md; момент анализа здесь не назначен.
