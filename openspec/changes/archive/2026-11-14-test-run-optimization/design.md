### Отдельные команды и порядок запуска

| Группа | Точка запуска и граница |
| --- | --- |
| Обычный pytest ядра | Штатная коллекция ядра за вычетом браузерной группы. `installer/test/test_installer.py` уходит из коллекции вместе с прежним вложенным запуском Node. Обычный режим сохраняет настройку `-n 12` из `pytest.ini` (F-02, F-06, F-11, F-14). |
| Браузерный pytest ядра | Отдельная коллекция браузерных тестов ядра и отдельный вызов pytest с `-n 2`. Внутренний сценарий с шестью драйверами остаётся в этой группе. При таймауте результат группы сообщает о таймауте и о результате очистки Chrome и профиля, относящихся к этому запуску (F-05, F-11, F-14, F-21). |
| Инсталлятор | `npm --prefix installer test` из корня выбранного ядра. Сохраняется штатный `pretest` со сборкой workflow и payload. Для дочерних Python-проверок используется интерпретатор выбранной среды ядра, которую прежде передавала обёртка pytest (F-02, F-06). |
| VS Code | Адресный режим передаёт выбранные входы сборке тестов VS Code и запускает соответствующие проверки. Сборка сохраняет проверку коллизий имён. Если выбранный вход исчез до сборки, итог называет группу и считает прогон незавершённым, даже если остальные тесты прошли. Контрактные тесты получают выбранный корень ядра через `SYMPHYSIS_ROOT` (F-03, F-04, F-06, F-07, F-10, F-23). |

Ручной запуск по инструкции и адресный исполнитель соблюдают один порядок внутри сессии. Сначала выполняются выбранные группы ядра, включая отдельный браузерный вызов, затем выбранный npm-набор инсталлятора, затем проверки плагина. Адресный исполнитель дожидается завершения каждой группы и прекращает последовательность при первой ошибке. Для GIGA IDE и OpenCode порядок применяется вручную (F-06, F-07, F-11).

### Построение адресного плана

1. **Получение путей.** У каждого участвующего репозитория свой корень и явно выбранная база. Режим изменения учитывает зафиксированные правки относительно базы, индекс, рабочее дерево и новые файлы. Режим коммита использует пути из сравнения коммита с родителем, выбранным явно для merge-коммита. Удаление учитывает прежний путь, переименование — оба пути (F-09).
2. **Отнесение путей к модулям.** Формат `dependencies` и идентичность `repo/module` берутся из действующих объявлений. Точки переиспользования — `read_declaration` для разбора README, `module` для разрешения имени и `owner` для принадлежности пути в `trace/trace_modules.py`. Для старого пути при переносе используются прежние объявления и связи, для нового — объявления соответствующего текущего состояния. Если прежних потребителей установить нельзя, применяется расширение по F-16 (F-03, F-08, F-09, F-16).
3. **Расчёт набора.** От модулей затронутых путей обход идёт к потребителям по обратным рёбрам `dependencies`, включая транзитивные связи. Тесты выбираются по принадлежности к модулю. Для общих фикстур, упаковочных и сквозных проверок используются их собственные связи с входными файлами и модулями, включая проверку VS Code при затронутом контракте ядра (F-04, F-07, F-08).
4. **Диагностика полноты.** Неизвестный путь, общая настройка, недоступные прежние связи при переносе и повреждённый README, из-за которого полноту подтвердить нельзя, расширяют применимый набор с указанием причины. При корректной декларации с неразрешённой целью остаётся сигнал, а обход продолжается по разрешённым связям. Ошибка Git или недоступное дерево дают незавершённый план с причиной (F-10, F-16, F-17, F-20).
5. **Вывод и исполнение.** План показывает корни, базы, выбранные группы и причины. Исполнитель использует эти группы и корни. В отчёте отдельно указываются источник отбора и фактическое рабочее состояние, если оно отличается от указанного коммита. Пустой diff, ноль выполненных тестов, сбой и недоступная обязательная проверка различимы в итоговом результате (F-06, F-09, F-10, F-18, F-23).

## Goals / Non-Goals

- Один и тот же состав тестовых групп для прямых команд и адресного исполнителя. Ручной порядок первого этапа задаёт порядок автоматического запуска второго этапа (F-06, F-07, F-11, F-14).
- Автоматический отбор ограничен ядром, инсталлятором и VS Code. Первый коммит без родителя вне объёма режима сравнения коммита (F-07, F-09, F-15).
- Отбор остаётся инструментом разработки Symphysis. Декларации README задают межмодульные связи, а сквозные тесты проверяют существующий контракт на явно выбранном рабочем дереве (F-04, F-08).

## Decisions

### F-06 Как запускать три набора после разделения pytest и npm-тестов инсталлятора?

- **Выбрано:** A. В первом этапе дать отдельные команды и описать порядок. Во втором дать команде выбора выполнить весь план последовательно: pytest ядра, инсталлятор при необходимости, затем плагин. Обычный прогон останавливается на первой ошибке. Для диагностики отдельную группу можно запустить напрямую. Цена — одна точка запуска должна корректно передавать коды возврата и среду, включая Python для npm.
- **Обратимость:** обратимо — Отдельные команды pytest, npm и плагина остаются доступны. Последовательный запуск можно заменить ручным вызовом без изменения тестов.
- **Улики выбранного:** openspec/changes/test-run-optimization/intent.md «Затем добавить команду, которая показывает, какие тесты выбраны и почему, и умеет их запустить.»
- **Улики выбранного:** openspec/changes/test-run-optimization/intent.md «тесты ядра и плагина одна сессия в одно время не запускает: сначала ядро, потом плагин.»
- **Улики выбранного:** installer/test/test_installer.py «str(Path(sys.executable).parent) + os.pathsep + os.environ.get("PATH", "")»
- **Улики выбранного:** installer/package.json «"pretest": "node scripts/build-workflow-carriers.js &amp;&amp; node scripts/sync-payload.js"»
- **Отвергнуто:** B. В обоих этапах запускать команды по отдельности. Команда выбора показывает весь план и запускает только явно указанную группу. Порядок обеспечивает разработчик по инструкции. Меньше оркестрации, но агенту проще случайно наложить прогоны друг на друга.
- **Отвергнуто:** C. Добавить общий локальный замок для запусков из разных сессий. Это ограничит суммарную нагрузку только для команд, которые пользуются замком. Понадобятся правила ожидания, отмены и очистки после сбоя. — маловероятно: В постановке указан порядок внутри одной сессии. Одновременные запуски независимых сессий пока не установлены как причина зависаний.

### F-07 Для каких плагинов в этом изменении делать автоматический выбор тестов?

- **Выбрано:** A. Начать с VS Code. Для GIGA IDE и OpenCode применять тот же порядок при ручных запусках. Их автоматический выбор рассмотреть после проверки подхода на основном плагине.
- **Обратимость:** обратимо — К существующему порядку можно добавить адаптеры GIGA IDE и OpenCode, когда будут проверены их сборки и наборы тестов.
- **Улики выбранного:** docs/repo-contract.md «VS Code — основная: функциональность плагина сперва появляется и проверяется в `symphysis-vscode`.»
- **Улики выбранного:** docs/repo-contract.md «GIGA IDE и opencode — порты: `symphysis-giga` и `symphysis-opencode` следуют за функциями плагина VS Code и держат свои файлы сборки.»
- **Улики выбранного:** vscode/build.mjs «Юнит-тесты: тесты модуля — в `src/&lt;модуль&gt;/test/`, общие и сквозные для нескольких модулей — в `test/unit/`»
- **Отвергнуто:** B. Сразу охватить VS Code, GIGA IDE и OpenCode. Для каждого порта нужно обследовать тестовый стенд, определить общие проверки и отдельно проверить выбор.
- **Отвергнуто:** C. Ограничить автоматизацию ядром и инсталлятором. Для VS Code оставить ручной запуск штатных команд. — маловероятно: Совместные правки входят в постановку, а у VS Code уже есть модульные тесты и отдельные сквозные сценарии.

### F-08 Откуда брать связи для выбора тестов затронутых модулей и их потребителей?

- **Выбрано:** C. Довести декларации `dependencies` в README до достаточной полноты и строить отбор на них. Общие, сквозные и упаковочные проверки потребуют своих связей. Изменится дисциплина ведения модульных README.
- **Слово человека (2026-11-13):** «Вариант C кажется немного более сложным, но более расширяемым и проверяем, чем A. Если вариант А оптимальнее -- напиши пожалуйста сравнение с вариантом C.»
- **Обратимость:** дорого — Переход на отдельную карту потребует перенести правила обратного обхода из деклараций модулей и повторно сверить выбор наборов на изменениях ядра и VS Code.
- **Улики выбранного:** trace/README.md «dependencies:»
- **Улики выбранного:** viewer/README.md «name: viewer»
- **Улики выбранного:** viewer/viewer_render.py «from journal_render import CONTRACT, _viewer_payload»
- **Улики выбранного:** pytest.ini «и сквозные проверки (справка всех входов, канон скиллов и водителей, хуки, документы контура разработки).»
- **Отвергнуто:** A. Использовать границы модулей и расположение тестов, добавить явные правила для потребителей, общих файлов, payload и межрепозиторного контракта. Выбирать транзитивных потребителей по этим связям. Начать с проверяемой карты и сверки того, что у каждого набора есть путь попадания в выбор. Цена — сопровождение правил при новых связях.
- **Отвергнуто:** B. Выводить прямые связи из импортов Python и TypeScript и дополнять их правилами для файлов, процессов и упаковки. Меньше ручных связей для обычного кода, больше работы на разбор разных языков, псевдонимов импортов и динамических зависимостей.
- **Отвергнуто:** D. Выбирать только каталог изменённого модуля. — маловероятно: Даже локальный импорт `viewer` из `decisions` даёт контрпример. Такой выбор может пропустить потребителя без изменений в его каталоге.

### F-09 Как команда определяет набор изменённых файлов для изменения и для отдельного коммита?

- **Выбрано:** A. Сделать явные режимы. Для изменения сравнивать с указанной базой в каждом участвующем репозитории и учитывать индекс, рабочее дерево и новые файлы. Для отдельного коммита сравнивать коммит с родителем, у merge-коммита явно определять родителя. Удаление и переименование учитывают исходный путь, а переименование — ещё и новый. План показывает корни и базы.
- **Обратимость:** обратимо — Можно добавить автоматический выбор базы, сохранив явное сравнение ревизий и рабочие деревья как вход команды.
- **Улики выбранного:** openspec/changes/test-run-optimization/intent.md «если модуль не был затронут изменением (или новым коммитом, если правка выполнена без создания изменения), то и гонять тесты всех модулей не обязательно.»
- **Улики выбранного:** skills-store/tools/pick_tests.py «Изменённые файлы: и в индексе, и в рабочем дереве, и новые.»
- **Улики выбранного:** skills-store/tools/pick_tests.py «Файлы, разошедшиеся с названной ревизией.»
- **Улики выбранного:** vscode/test/core-files.mjs «export const coreRoot = (env, sibling) =&gt; env.SYMPHYSIS_ROOT || sibling;»
- **Отвергнуто:** B. По умолчанию выводить базу из текущей ветки, upstream и состояния рабочего дерева. Для неоднозначных случаев дать явные параметры. Меньше аргументов в обычной работе, но режим приходится проверять после коммита, на detached HEAD и при двух репозиториях.
- **Отвергнуто:** C. Принимать только список файлов от разработчика. Это годится для ручного первого этапа, но во втором человек сам отвечает за полноту двух diff. — маловероятно: Пропущенный путь в переданном списке неотличим от отсутствия изменений.

### F-10 Что делать, если область влияния или возможность выполнить выбранный набор не подтверждена?

- **Выбрано:** A. Для читаемого diff с неизвестным путём или общей настройкой расширять план до нужного полного набора и показывать причину. Ошибку Git, отсутствующий worktree и обязательную, но недоступную проверку выводить как незавершённый прогон. Пустой diff и ноль выполненных проверок показывать отдельно от успешного запуска.
- **Обратимость:** обратимо — Правило расширения набора и исход ошибки можно менять в команде выбора. Сами тесты и связи модулей от этого не меняются.
- **Улики выбранного:** skills-store/CLAUDE.md «неизвестный путь даёт **весь набор, а не пустой**»
- **Улики выбранного:** pytest.ini «и сквозные проверки (справка всех входов, канон скиллов и водителей, хуки, документы контура разработки).»
- **Улики выбранного:** vscode/test/core-files.mjs «export const coreRoot = (env, sibling) =&gt; env.SYMPHYSIS_ROOT || sibling;»
- **Улики выбранного:** docs/repo-contract.md «Тесты плагина с `SYMPHYSIS_ROOT` на worktree `main` ядра проходят без пропусков.»
- **Отвергнуто:** B. На любой неопределённости остановиться и попросить явный набор. Это предотвращает неожиданно тяжёлый запуск, но делает обычную работу зависимой от ручного решения даже при известном корне и доступных тестах.
- **Отвергнуто:** C. Проверить только уверенно выбранные группы, остальные показать в отчёте. Можно быстро получить частичный результат, но его легко принять за достаточную проверку. — маловероятно: Неполный выбор для обязательной проверки может дать внешне зелёный результат.

### F-11 Как выполнить исключение для браузерных тестов и учесть сценарий очистки профилей под нагрузкой?

- **Выбрано:** A. В первом этапе выделить браузерные тесты в отдельный профиль ядра и запускать его последовательно с остальными группами. Сравнить один поток выполнения и малые значения xdist на одном наборе. Выбрать самый быстрый из режимов, которые проходят повторные прогоны без плавающих падений, таймаутов и оставшихся профилей. Сценарий, который намеренно запускает шесть драйверов, сохраняет свою нагрузку.
- **Обратимость:** обратимо — Лимит воркеров браузерной группы можно изменить и заново замерить на том же наборе. Сценарий очистки профилей сохраняет свои шесть драйверов.

Для проверки разбиения сравнить идентификаторы собранных тестов двух групп с полной коллекцией pytest ядра после отделения инсталлятора. Проверить пустое пересечение и равенство объединения полной коллекции (F-06, F-11, F-14, F-22).
2. Дополнить декларации зависимостей ядра и VS Code, связать общие и сквозные проверки с их входами, подключить адресное построение и последовательное выполнение плана. До появления адресного режима отдельные группы выбираются вручную (F-06, F-07, F-08, F-09).
3. Сравнить прогоны до и после по трём случаям из спеки и отдельно проверить полный режим. Измерение из [F-11](research/F-11.md) служит основанием браузерного лимита. Базовый замер всего изменения даёт данные для согласования числового порога (F-11, F-13, F-14).
4. После появления адресного режима на интеграции применяется адресный план. Полный прогон выполняется на выпуске или по решению владельца. Для выпуска VS Code в полный режим входят проверки на выбранном `main` ядра без пропусков и `npm run e2e:vsix` по действующему контракту (F-04, F-12).
