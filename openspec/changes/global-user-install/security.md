## Границы доверия

Доверенный источник кода/mermaid/клиентских шаблонов — закреплённая поставка и проверенный manifest. Журнал, brief, карта корней, planning config, план миграции и сообщения форка — данные, даже если внутри написана команда или рекомендация поменять разрешения. Нативная оболочка агента исполняется с полномочиями родителя; установка symphysis не создаёт ему дополнительную изоляцию или право обходить ограничения клиента.

Проектные секреты, ответы, черновики и карта корней остаются у выбранного store. Локальный resolver JSON содержит пути для процесса на той же машине, а HTML/публикуемые отчёты этих личных путей не получают. Явно настроенный внешний корень улик допустим; выход за его конечную границу из-за `..`, ссылки или ошибочной базы недопустим.

## Применение к принятому дизайну

- Manifest и план миграции разбираются как строгие данные: неизвестный формат, абсолютный хвост, выход за разрешённую цель, неизвестное происхождение или смена realpath не дают права записи. Данные плана не исполняются как shell. Повторное сравнение F-16 обязательно непосредственно перед применением; подтверждение не является бессрочным разрешением перезаписать изменившийся файл.
- `ProjectContext` не является новым механизмом авторизации. Даже если его сериализация пришла из окружения, пути/поколение сверяются с выбранным manifest и адресуемым store; поздний селектор другой цели отвергается. У обхода старого прямого CLI нет выдуманной OS-защиты: штатные носители обязаны пройти preflight, что ещё предстоит подтвердить в журнале клиента по F-23.
- Discovery `resolve` не разрешает отдельный незакрытый lease запуск Python хостом. Поддерживаемый host/global-entrypoint делегирует исполнение dispatcher, который удерживает lease до выхода инструмента. В preflight сравнивается эффективная схема команды/change с учётом metadata и argv, чтобы проверка одной схемы не прикрывала исполнение другой.
- Bootstrap плагина ищется в явной конфигурации либо окружении исполняющего IDE host; cwd/workspace не становятся неявным источником программы. Launcher передаёт argv отдельно и проверяет resolver handshake до действий над store. Сам факт обнаружения CLI не подтверждает его контракт, готовность runtime или безопасность прямого Python-вызова.
- Установщик сначала проверяет структуру planning config и конфликты, затем пишет. Он не подставляет сырые пользовательские значения в шаблон агента или permissions. Неизвестная нативная версия/форма — неподтверждённая интеграция с диагностикой, не повод копировать Claude frontmatter всем.
- Сборочные `removeTree` и dev worktree-порядок не служат реализацией пользовательского удаления. Обновление удаляет только перечисленные собственные временные файлы после проверки реальных границ. При аварийном восстановлении также нельзя следовать вложенной ссылке и стирать её цель.
- Тела скиллов, включаемые в HTML, берутся из выбранной поставки. Автоматического включения личной карты, config, auth-файлов, произвольных документов по ссылкам либо trace stdout в страницу нет. Текст из журналов не попадает в слот исполняемой библиотеки.

## Статус проверки

Проверка проектирования выполнена чтением specs, code/probes и независимым read-only разбором. Таблица выше фиксирует основания на этапе design. Resolver, planner, leases, адаптеры и HTML loader затем реализованы; свидетельства этапа apply приведены отдельно ниже. Реальная загрузка инструкций и ограничений нативными клиентами ещё не подтверждена. Канон не добавлен новыми запретами в журнал; решения владельца и исходная опись последствий не переписаны.

Будущая приёмка должна включать независимые local/global фикстуры, reparse/права, конфликт чужого файла, старую карту `<root>`, гонку preview, неправильный planning config, одноимённые change в двух store, свежие native sessions и автономную страницу на разных дисках. Скриптовый успех, наличие файла и прогноз поведения модели не заменяют эти свидетельства.
