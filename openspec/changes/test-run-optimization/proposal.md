# Proposal

## Why

Сократить время повседневных проверок Symphysis и пиковую нагрузку от одновременно работающих тестовых наборов. Оптимизация относится к контуру разработки ядра и плагина. Эффект проверяется по времени, нагрузке и составу выполненных тестов (F-02, F-03, F-05, F-06, F-08, F-13).

## What Changes

- **Этап 1. Отдельные команды.** **BREAKING** для сценариев разработки, где одна команда pytest считалась полной проверкой ядра и инсталлятора. Pytest ядра и npm-тесты инсталлятора запускаются отдельно. В одной сессии выбранные группы выполняются последовательно в порядке «pytest ядра → npm-тесты инсталлятора при необходимости → тесты плагина». На этом этапе разработчик выбирает группы и тесты модулей вручную по инструкции (F-06, F-07, F-08).
- **Этап 1. Браузерные тесты.** Браузерная группа ядра выполняется отдельным вызовом pytest с `-n 2`, последовательно с остальными группами. Сценарий очистки профилей под нагрузкой сохраняет запуск шести драйверов внутри теста (F-11, F-14).
- **Этап 2. Адресный выбор.** Команда показывает корни репозиториев, базы сравнения, выбранные проверки и причины выбора. Для изменения сравнение с указанной базой учитывает индекс, рабочее дерево и новые файлы. Для отдельного коммита сравнение идёт с родителем, для merge-коммита родитель задаётся явно. При удалении учитывается прежний путь, при переименовании — оба пути (F-06, F-09).
- **Этап 2. Связи и полнота выбора.** Выбор охватывает затронутые модули и их транзитивных потребителей по `dependencies` в README, а также применимые общие, сквозные и упаковочные проверки. Общая настройка или неизвестный путь расширяют план до применимого полного набора с объяснением причины. Ошибка Git, недоступное рабочее дерево или обязательная проверка, которую невозможно выполнить, дают незавершённый прогон. Пустой diff и ноль выполненных проверок имеют отдельный результат (F-04, F-08, F-10).
- **Этап 2. Выполнение плана.** Команда последовательно запускает выбранные группы и останавливается на первой ошибке. Отдельные команды остаются доступны для диагностики. Автоматический выбор охватывает ядро, инсталлятор и VS Code. Для GIGA IDE и OpenCode тот же порядок применяется при ручном запуске (F-06, F-07).
- **Интеграция и выпуск.** После появления адресного режима на интеграции используется адресный план. Полный прогон выполняется на выпуске или по решению владельца (F-12).
- **Проверка эффекта.** Сравниваются прогоны до и после на одной машине и сопоставимых ревизиях. Контрольные случаи включают локальную правку модуля, общую или контрактную правку и совместную правку ядра с плагином. Сравнение учитывает состав и пропуски тестов, время, пиковую нагрузку по числу воркеров и дочерних процессов, таймауты и очистку. Отдельно проверяется полный режим. Числовой порог согласуется по базовому замеру (F-13).

## Capabilities

### New Capabilities

- `test-impact-selection` — расчёт и объяснение плана проверок по Git-изменениям, зависимостям модулей и связям общих, сквозных и упаковочных проверок. Сюда входят расширение плана при неизвестной области влияния и диагностика неполных входных данных (F-04, F-08, F-09, F-10).
- `test-run-execution` — отдельные команды тестовых групп, порядок их выполнения, браузерный прогон с `-n 2`, результаты выполнения и условия применения адресного и полного прогонов (F-06, F-07, F-10, F-11, F-12, F-14).

### Modified Capabilities

- `module-declaration` — README модулей ядра и VS Code поддерживают декларации `dependencies`, достаточные для выбора тестов потребителей (F-08).

## Impact

- Ядро и инсталлятор — конфигурация pytest, обёртка Node-тестов инсталлятора, браузерный набор и команды разработчика. При раздельном запуске npm-тестов сохраняется доступ к нужному интерпретатору Python (F-02, F-06, F-11, F-14).
- Ядро и VS Code — модульные README, сборка и запуск выбранных тестов, контрактные проверки на выбранном рабочем дереве ядра (F-03, F-04, F-07, F-08, F-09).
- Контур разработки — инструкции по ручному и адресному запуску, правила интеграции и выпуска, сравнительные прогоны (F-06, F-07, F-12, F-13).
