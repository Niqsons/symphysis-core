# Spec Delta

## Purpose

Выполнять проверки разработки Symphysis отдельными группами в последовательном порядке и показывать исходы адресного и полного прогонов.

## ADDED Requirements

### Requirement: Проверки доступны отдельными командами
Контур разработки SHALL предоставлять самостоятельные команды pytest ядра и npm-тестов инсталлятора и инструкции по ручному выбору тестов модулей и порядку запуска групп. Команда pytest ядра MUST NOT запускать npm-набор инсталлятора. Отдельные группы SHALL оставаться доступными для диагностики, а npm-тесты SHALL получать нужную среду Python (F-02, F-06, F-07).

#### Scenario: Отдельный запуск pytest
- **GIVEN** разработчик выбрал только pytest ядра
- **WHEN** он запускает команду этой группы
- **THEN** тесты ядра выполняются без запуска npm-набора инсталлятора

#### Scenario: Тесты инсталлятора требуют Python
- **GIVEN** среда тестов ядра указывает интерпретатор Python с нужными зависимостями, а в PATH есть другой интерпретатор
- **WHEN** выполняется npm-набор инсталлятора в той же сессии
- **THEN** его Python-проверки используют интерпретатор из выбранной среды

#### Scenario: Ручной выбор по модулю
- **GIVEN** разработчик знает, какой модуль изменился
- **WHEN** он следует инструкции по ручному запуску
- **THEN** инструкция позволяет выбрать тесты модуля, запустить нужную группу и определить её место в последовательности

### Requirement: Браузерная группа ядра запускается отдельно с двумя воркерами
Браузерные тесты ядра SHALL выполняться отдельным вызовом pytest с двумя воркерами xdist (`-n 2`), последовательно с остальными группами. Сценарий очистки профилей под нагрузкой SHALL сохранять запуск шести драйверов внутри теста (F-11, F-14).

#### Scenario: Совместная проверка ядра и браузера
- **GIVEN** в план вошли обычные и браузерные тесты ядра
- **WHEN** выполняется план
- **THEN** браузерные тесты выполняются ровно в отдельном вызове pytest с двумя воркерами и не пересекаются по времени с обычными тестами

#### Scenario: Проверка очистки профилей под нагрузкой
- **GIVEN** в браузерный прогон входит тест очистки профилей
- **WHEN** выполняется этот тест
- **THEN** тест запускает шесть драйверов и проверяет их завершение и удаление профилей

### Requirement: План выполняется последовательно и останавливается на первой ошибке
В одной сессии выбранные проверки SHALL выполняться последовательно в порядке ядро, инсталлятор, плагин. Адресная команда SHALL выполнить этот порядок автоматически и остановиться на первой ошибке с ненулевым кодом. Сквозные тесты VS Code SHALL использовать выбранное рабочее дерево ядра. Для GIGA IDE и OpenCode порядок SHALL применяться при ручных прогонах (F-04, F-06, F-07, F-11).

#### Scenario: План содержит ядро, инсталлятор и VS Code
- **GIVEN** план выбрал три группы
- **WHEN** каждая группа завершается успешно
- **THEN** инсталлятор стартует после завершения ядра, а VS Code — после завершения инсталлятора

#### Scenario: Инсталлятор не выбран
- **GIVEN** план включает ядро и VS Code без инсталлятора
- **WHEN** выполняется план
- **THEN** VS Code стартует после завершения ядра

#### Scenario: Соседний клон ядра на другой ревизии
- **GIVEN** план выбрал ядро из рабочего дерева изменения, а рядом с VS Code есть клон ядра на другой ревизии
- **WHEN** запускается выбранная сквозная проверка VS Code
- **THEN** проверка использует рабочее дерево ядра из плана

#### Scenario: Первая группа завершилась ошибкой
- **GIVEN** план включает проверки ядра и плагина
- **WHEN** ядро завершает проверку с ненулевым кодом
- **THEN** команда сообщает о сбое ядра, возвращает ненулевой код и не запускает плагин

### Requirement: Невыполненные проверки видны в результате
Команда SHALL отличать успешно выполненные проверки от пустого сравнения, нуля выполненных проверок и незавершённого прогона. Недоступное рабочее дерево, ошибка Git или недоступная обязательная проверка SHALL давать незавершённый исход с указанием причины (F-10).

#### Scenario: Обязательная проверка пропущена
- **GIVEN** для запланированной обязательной проверки отсутствует необходимый стенд
- **WHEN** команда выполняет план
- **THEN** итог называет недоступную проверку и сообщает, что прогон не завершён

#### Scenario: Ни один тест не выполнился
- **GIVEN** план содержит группу, а её запуск завершился без выполненных проверок
- **WHEN** команда выводит результат
- **THEN** она явно сообщает о нуле выполненных проверок

### Requirement: Отчёт указывает проверенное рабочее состояние
Отчёт о прогоне MUST NOT выдавать проверку рабочего дерева, содержимое которого отличается от указанного коммита, за проверку этого коммита. При таком расхождении отчёт SHALL различать коммит, использованный для отбора тестов, и рабочее состояние, на котором тесты выполнены (F-18).

#### Scenario: План по коммиту выполнен на дереве с правками

- **GIVEN** тесты выбраны по указанному коммиту, а рабочее дерево содержит правки поверх него
- **WHEN** выбранные тесты выполняются на этом рабочем дереве
- **THEN** отчёт указывает коммит как источник отбора и сообщает, что тесты выполнялись на рабочем дереве с правками

### Requirement: Адресный и полный прогоны применяются на разных этапах
После появления адресного режима проверки при интеграции SHALL выполняться по адресному плану. Полный прогон SHALL выполняться на выпуске или по решению владельца и охватывать применимые тестовые группы (F-12).

#### Scenario: Интеграция адресной правки
- **GIVEN** адресный режим доступен, а изменение затрагивает один модуль и его потребителей
- **WHEN** изменение проверяется при интеграции
- **THEN** выполняется адресный план этого изменения

#### Scenario: Полная проверка перед выпуском или по слову владельца
- **GIVEN** готовится выпуск или владелец поручил полный прогон после нескольких изменений
- **WHEN** запускается проверка
- **THEN** выполняются все применимые группы с их режимами и последовательностью

### Requirement: Эффект адресного запуска проверяется сравнительным замером
При приёмке оптимизации контур разработки SHALL сравнить прогоны до и после на одной машине и сопоставимых ревизиях. Отчёт SHALL показывать состав выполненных и пропущенных проверок, время, пики числа воркеров и дочерних процессов, таймауты и очистку. Полный режим проверяется отдельно. Числовой порог согласуется по базовому замеру (F-13).

#### Scenario: Сопоставимые прогоны на трёх типах правки
- **GIVEN** подготовлены локальная правка модуля, общая или контрактная правка и совместная правка ядра и плагина
- **WHEN** сравниваются прогоны до и после оптимизации
- **THEN** отчёт показывает метрики и состав проверок по каждому случаю, а результат полного режима приведён отдельно
