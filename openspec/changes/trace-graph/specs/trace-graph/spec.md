# Spec Delta

## Purpose
Граф трассируемости изменения: узлы и связи, которые скрипт собирает из файлов изменения. Живым файлом граф не хранится и напрямую не правится.

## ADDED Requirements

### Requirement: Граф собирается из файлов изменения
Скрипт графа, рабочее имя `tools/trace_graph.py`, SHALL собирать граф изменения из его файлов на любом шаге: граф равен тому, что уже написано (F-18, F-25, F-39). Напрямую граф SHALL NOT править никто: связь меняется только правкой файла изменения (F-30).

#### Scenario: Только что созданное изменение
- **GIVEN** изменение, где есть только `.openspec.yaml`
- **WHEN** скрипт собирает граф
- **THEN** граф пуст, код 0

#### Scenario: Граф растёт вместе с артефактами
- **GIVEN** изменение с журналом, граф несёт только записи
- **WHEN** появляется `specs/<capability>/spec.md` и скрипт собирает граф снова
- **THEN** в графе есть требования и сценарии этого файла, отдельного шага наполнения не было

#### Scenario: Связь правится через файл
- **GIVEN** требование с `(F-19)`, в графе есть его связь с `rec:F-19`
- **WHEN** в тексте требования номер заменён на `(F-20)` и скрипт собирает граф снова
- **THEN** в графе есть связь с `rec:F-20`, а связи с `rec:F-19` нет

### Requirement: Граф несёт связи артефактов с местом в файле
Граф SHALL нести связи, записанные в артефактах: capability и требование, сценарий и требование, требование и запись журнала, задача и сценарий, задача и запись, пункт security и требование, ветка отказа и сценарий; у каждой связи SHALL быть место `at` от каталога изменения (F-06, F-56, F-70). Смысл связи граф SHALL NOT судить: это делает атака (F-19).

#### Scenario: Связь называет место
- **GIVEN** требование с `(F-19)` в строке 6 файла `specs/demo/spec.md`
- **WHEN** скрипт собирает граф
- **THEN** связь `traces` к `rec:F-19` несёт `at` со значением `specs/demo/spec.md:6`

#### Scenario: Настоящее имя, неверный смысл
- **GIVEN** задача называет существующий сценарий, которого по смыслу не закрывает
- **WHEN** скрипт собирает граф
- **THEN** связь `satisfies` есть, сигнала о ней нет

### Requirement: Скрипт сам разбирает спеки с номерами строк
Скрипт SHALL сам разбирать заголовки `### Requirement:`, `#### Scenario:` и секции дельты и SHALL знать номер строки каждого узла (F-40). Тест SHALL сверять счётчики разбора с `openspec show --json` на фикстурах, расхождение с OpenSpec даёт красный тест (F-14, F-40).

#### Scenario: Узел несёт пометку дельты
- **GIVEN** спека с секциями `## ADDED Requirements` и `## MODIFIED Requirements`
- **WHEN** скрипт собирает граф
- **THEN** каждое требование несёт пометку своей секции и номер строки заголовка

#### Scenario: Счётчики разошлись с OpenSpec
- **GIVEN** фикстура, где разбор скрипта и `openspec show --json` дают разное число сценариев
- **WHEN** идёт тест сверки
- **THEN** тест красный и называет фикстуру

### Requirement: Живой граф не лежит на диске
Скрипт SHALL выводить граф в JSON или писать его в путь из `--out`; постоянного живого файла в каталоге изменения SHALL NOT быть (F-03, F-41).

#### Scenario: Вывод без файла
- **GIVEN** изменение с артефактами
- **WHEN** скрипт запущен без `--out`
- **THEN** граф выведен, новых файлов в каталоге изменения нет

#### Scenario: Запись в указанный файл
- **GIVEN** изменение с артефактами
- **WHEN** скрипт запущен с `--out <путь>`
- **THEN** по этому пути лежит граф, файлы изменения не изменены

### Requirement: Сохранённый граф проверяется скриптом
Проверка SHALL читать сохранённый файл графа, сверять его форму и хеши исходников с текущими файлами и SHALL давать сигнал «устарел» с именем разошедшегося файла; сигнал SHALL NOT менять код выхода (F-03, F-31, F-41).

#### Scenario: Файл свежий
- **GIVEN** файл графа, собранный из текущих файлов изменения
- **WHEN** идёт проверка
- **THEN** сигналов нет, код 0

#### Scenario: Исходник изменён
- **GIVEN** файл графа, а затем правка `tasks.md`
- **WHEN** идёт проверка
- **THEN** сигнал «устарел» называет `tasks.md`, код 0

#### Scenario: Форма не та
- **GIVEN** файл без поля `format`
- **WHEN** идёт проверка
- **THEN** сигнал называет файл и что в нём не так, код 0

### Requirement: Id читаемы, файл несёт версию формата
Узлы SHALL нести читаемые id: `req:capability/имя`, `scn:capability/требование/имя`, `rec:F-NN`, `task:N.M`. Файл SHALL нести `format: 1`, кандидат связи `source` (F-23, F-70). предположение: формы id у capability, пункта security и ветки отказа F-70 не называет; решить в design.

#### Scenario: Одно имя в двух capability
- **GIVEN** требование с одним именем в двух capability
- **WHEN** скрипт собирает граф
- **THEN** это два узла с разными id

#### Scenario: Переименование меняет id
- **GIVEN** требование переименовано в спеке
- **WHEN** скрипт собирает граф
- **THEN** узел несёт новый id, старого в графе нет

### Requirement: Связи между требованиями вычисляются как кандидаты
Скрипт SHALL вычислять пары требований с общими записями журнала и класть их в граф как кандидатов с `source`, отдельно от записанных связей; в отчёт сигналов кандидаты SHALL NOT идти (F-71).

#### Scenario: Общая запись
- **GIVEN** два требования, оба с `(F-19)`
- **WHEN** скрипт собирает граф
- **THEN** в графе кандидат на эту пару с `source`, в отчёте сигналов строки о ней нет

### Requirement: Новый артефакт схемы проверяется на вход в граф
Реестр в скрипте SHALL называть на каждый артефакт схемы, что граф из него берёт, значение `ничего` законно. Тест SHALL сверять реестр с `schema.yaml`. Правило SHALL быть описано абзацем в `CLAUDE.md` (F-53).

#### Scenario: Артефакт без строки реестра
- **GIVEN** в `schema.yaml` добавлен артефакт, строки в реестре нет
- **WHEN** идут тесты
- **THEN** тест красный и называет артефакт

#### Scenario: Артефакт, из которого брать нечего
- **GIVEN** строка реестра со значением `ничего`
- **WHEN** идут тесты
- **THEN** тест зелёный, узлов из этого артефакта в графе нет
