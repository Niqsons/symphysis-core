# Spec Delta

## Purpose
Отчёт сигналов графа: что он называет, как соединён с `openspec validate`, когда его показывают человеку и как записывается ответ на сигнал.

## ADDED Requirements

### Requirement: Одна команда отчитывается и за граф, и за validate
Скрипт графа SHALL сам запускать `openspec validate --json` и выводить его находки вместе с сигналами графа одним отчётом. Форк OpenSpec для этого SHALL NOT меняться (F-05, F-07, F-32).

#### Scenario: Находка validate в отчёте
- **GIVEN** требование без сценария
- **WHEN** скрипт собирает отчёт
- **THEN** отчёт несёт находку `openspec validate` рядом с сигналами графа

#### Scenario: Находок нет
- **GIVEN** изменение, где `openspec validate` чист и сигналов графа нет
- **WHEN** скрипт собирает отчёт
- **THEN** отчёт говорит, что сигналов нет, код 0

#### Scenario: `openspec` не запустился
<!-- F-93 -->
- **GIVEN** `openspec` нет или он завершился ошибкой
- **WHEN** скрипт собирает отчёт
- **THEN** отчёт несёт сигналы графа и строку «validate не запустился» с причиной, код 0

### Requirement: Сигналы не останавливают работу
Сигнал SHALL только называть зазор и SHALL NOT менять код выхода скрипта; решает человек: реализовать или принять (F-31).

#### Scenario: Отчёт с сигналами
- **GIVEN** изменение с требованием без задачи
- **WHEN** скрипт собирает отчёт
- **THEN** сигнал назван, код 0
<!-- проба краёв: форма=io, исходы: нет -->
<!-- проба запретов: исходы: F-112 Specify -->

### Requirement: Сигнал не повод расширять работу
Сигнал MUST NOT становиться основанием для правки спек и задач без слова человека: модель называет зазор, решает человек (F-31, F-112; проверка — суждение: человек сверяет diff реализации с отчётом и своими ответами).

#### Scenario: Модель видит зазор
<!-- F-112 -->
- **GIVEN** отчёт называет требование без задачи, человек о нём не решал
- **WHEN** модель продолжает реализацию
- **THEN** в `tasks.md` и спеках из-за этого сигнала правок нет; человек сверяет это по diff
<!-- требование из F-112; пробами не проходило -->

### Requirement: Отчёт называет закрытый состав сигналов
Отчёт SHALL называть: критерий без требования; требование и сценарий без задачи; требование без записи (F-83); решение без требования и задачи; неоднозначное имя; неизвестное имя или номер; задачу ни к чему; след, отставший от журнала (F-64); сценарий MODIFIED с прежним именем и другим текстом (F-95). Решение об объёме SHALL оставаться обычной строкой этого вида (F-65).

#### Scenario: Критерий без требования
- **GIVEN** факт `постановка`, на который не ссылается ни одно требование
- **WHEN** скрипт собирает отчёт
- **THEN** сигнал называет запись и цитату критерия

#### Scenario: Решение об объёме
- **GIVEN** решение об объёме работ, до которого не дошли ни требование, ни задача
- **WHEN** скрипт собирает отчёт
- **THEN** оно названо строкой вида «решение без требования и задачи», отдельной пометки у него нет

#### Scenario: Одно имя у двух требований capability
<!-- F-94 -->
- **GIVEN** одно имя сценария у двух требований capability `demo` и задача с этим именем
- **WHEN** скрипт собирает отчёт
- **THEN** оба сценария считаются закрытыми, сигнал «неоднозначное имя» называет оба требования
<!-- проба краёв: форма=collection, исходы: F-94 Specify -->
<!-- проба запретов: исходы: нет; канон — F-59 → security.md -->

### Requirement: Шумные виды в отчёт не идут
Отчёт SHALL NOT называть: улику, разошедшуюся с файлом, она остаётся у `check`; сценарий и требование, перенесённые из мастера в MODIFIED без изменения текста; пункт security с известным именем или без имени; решение «Оставить как есть» (F-57, F-64, F-95).

#### Scenario: Улика разошлась
- **GIVEN** улика журнала, цитаты которой больше нет в файле
- **WHEN** скрипт собирает отчёт
- **THEN** строки о ней нет, `journal.py check` её называет

#### Scenario: MODIFIED несёт прежний сценарий
- **GIVEN** требование в MODIFIED со сценарием, который уже есть в мастер-спеке с тем же текстом, и без задачи на него
- **WHEN** скрипт собирает отчёт
- **THEN** строки об этом сценарии нет

#### Scenario: Новый сценарий в MODIFIED
- **GIVEN** требование в MODIFIED со сценарием, которого в мастер-спеке нет, и без задачи на него
- **WHEN** скрипт собирает отчёт до `/opsx:sync`
- **THEN** сигнал называет этот сценарий

#### Scenario: Пункт security закрыт доводом
- **GIVEN** пункт security без имени требования, закрытый доводом
- **WHEN** скрипт собирает отчёт
- **THEN** строки о нём нет; пункт с неизвестным именем требования сигнал называет

#### Scenario: Прежнее имя, другой текст
<!-- F-95 -->
- **GIVEN** MODIFIED со сценарием, имя которого есть в мастере, а текст другой, и без задачи на него
- **WHEN** скрипт собирает отчёт до `/opsx:sync`
- **THEN** сигнал называет сценарий, в сохранённом отчёте такие расхождения идут отдельным разделом

### Requirement: Сигнал о решении следует его исходу
Запись с исходом Specify без сценария и запись с исходом Backstop без задачи SHALL давать сигнал, исходы Dismiss и Defer SHALL молчать (F-64). Связь Specify со сценарием SHALL считаться по точному совпадению с комментарием `<!-- F-NN -->` под заголовком сценария (F-45).

#### Scenario: Specify с комментарием
- **GIVEN** запись F-12 с исходом Specify и сценарий с `<!-- F-12 -->` под заголовком
- **WHEN** скрипт собирает отчёт
- **THEN** сигнала о F-12 нет

#### Scenario: Specify без комментария
- **GIVEN** запись F-12 с исходом Specify, сценария с её номером нет
- **WHEN** скрипт собирает отчёт
- **THEN** сигнал называет F-12

#### Scenario: Dismiss
- **GIVEN** запись с исходом Dismiss без требования и задачи
- **WHEN** скрипт собирает отчёт
- **THEN** строки о ней нет

### Requirement: Сигнал называет запись, снявшую исход
Рядом с сигналом «Specify без сценария» отчёт SHALL называть запись, у которой эта запись стоит в `depends_on`: вероятная причина, почему сценария нет (F-11, F-46). Этот случай SHALL проверяться фикстурой в тестах (F-69).

#### Scenario: Исход снят позже
- **GIVEN** запись F-12 с исходом Specify без сценария и решённая запись F-30 с `depends_on: [F-12]`
- **WHEN** скрипт собирает отчёт
- **THEN** строка о F-12 несёт «снято F-30?»

### Requirement: Отчёт показывается перед реализацией и в её конце
Инструкция `apply` SHALL велеть модели перед первой задачей и в конце реализации, когда отмечена последняя задача, собрать отчёт и отдать человеку ссылку на его файл (F-48, F-78, F-113). предположение: до первой задачи файл лежит в `graph/` без снимка, а `/opsx:archive` считает такой каталог неполным; решить в design.

#### Scenario: Перед первой задачей
- **GIVEN** изменение без отмеченных задач
- **WHEN** начинается `/opsx:apply`
- **THEN** человек получает ссылку на файл отчёта до первой правки кода

#### Scenario: После последней задачи
- **GIVEN** отмечена последняя задача `tasks.md`
- **WHEN** модель заканчивает реализацию
- **THEN** человек получает ссылку на файл отчёта, собранного на текущих файлах

### Requirement: Отчёт отдаётся ссылкой
Модель MUST NOT пересказывать отчёт и отбирать из него строки: человеку SHALL отдаваться ссылка на файл отчёта, и всё. Отчёт может быть большим и не влезть в предел вывода модели (F-31, F-113; проверка — суждение: человек сверяет чат с файлом).

#### Scenario: Модель отдаёт отчёт
<!-- F-113 -->
- **GIVEN** отчёт собран
- **WHEN** модель отдаёт его человеку
- **THEN** в чате ссылка на файл отчёта, пересказа и отбора строк нет
<!-- требование из F-113; пробами не проходило -->

### Requirement: Ответ на сигнал записывается в журнал
Ответ человека на сигнал SHALL быть записью журнала с вопросом `[сигнал] <вид> · <ключ>`, исходами Specify, Dismiss, Backstop, Defer и `outcome.kind: проба`. Запись SHALL заводиться только на сигнал, о котором человек решил что-то записать; скрипт SHALL находить её и этот сигнал больше не поднимать (F-30, F-47, F-98). При решении Specify строка `apply.instruction` SHALL велеть написать `outcome` и сценарий (F-99).

#### Scenario: Человек принял зазор
- **GIVEN** сигнал о требовании без задачи и запись `[сигнал]` об этом требовании с исходом Dismiss через `apply`
- **WHEN** скрипт собирает отчёт
- **THEN** этого сигнала в отчёте нет

#### Scenario: Человек ничего не записал
- **GIVEN** тот же сигнал и записи `[сигнал]` нет
- **WHEN** скрипт собирает отчёт
- **THEN** сигнал назван снова

#### Scenario: Запись отвечает на один сигнал
<!-- F-98 -->
- **GIVEN** запись с вопросом `[сигнал] требование без задачи · demo/Имя`
- **WHEN** скрипт собирает отчёт
- **THEN** молчит только сигнал этого вида и этого ключа

#### Scenario: Решение Specify у записи `[сигнал]`
<!-- F-99 -->
- **GIVEN** запись `[сигнал]` с решением Specify
- **WHEN** идёт `/opsx:apply`
- **THEN** по строке `apply.instruction` модель пишет `outcome` и сценарий с `<!-- F-NN -->`

### Requirement: Запись `[сигнал]` без решения не снимает сигнал
Запись `[сигнал]` без `decision` MUST NOT снимать сигнал: сигнал снимает только решение человека, иначе модель очистит отчёт сама (F-30, F-47, F-114; проверка — тест).

#### Scenario: Запись без решения
<!-- F-114 -->
- **GIVEN** сигнал о требовании без задачи и запись `[сигнал]` об этом требовании без `decision`
- **WHEN** скрипт собирает отчёт
- **THEN** сигнал назван
