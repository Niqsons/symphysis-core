# Spec Delta

## ADDED Requirements

### Requirement: Структурная ось содержит все объявленные модули состава
Граф SHALL содержать узлы компонентов, объявленных repo и всех корректно обнаруженных модулей участвующих repo, включая модули без связей с требованиями. Состав компонентов и repo образует структурные связи. Посторонние доступные локальные деревья не становятся участниками только из-за доступности (F-01, F-02, F-16, F-17).

#### Scenario: Модуль без аннотации реализации
- **GIVEN** repo содержит два модуля, требование явно связано только с одним
- **WHEN** собран граф
- **THEN** оба модуля присутствуют; отсутствие аннотации у второго не скрывает его

#### Scenario: Два repo одного компонента
- **GIVEN** состав связывает один компонент с двумя repo
- **WHEN** собран граф
- **THEN** компонент, оба repo и их модули различимы структурными связями

### Requirement: Структурные id различают репозиторий и модуль
Структурные узлы SHALL иметь читаемые устойчивые id: модуль различается логическим repo и именем, файл — repo и относительным путём. Имя каталога клона или абсолютный путь MUST NOT становиться идентичностью repo/module. Одинаковое имя модулей разных repo не сливается, а id требования остаётся независимым от модульной оси (F-04, F-14, F-17, F-31).

#### Scenario: Одно имя модулей
- **GIVEN** repo core и plugin объявляют viewer
- **WHEN** строится граф
- **THEN** модули имеют разные id и не смешивают свои связи реализации

#### Scenario: Другой каталог клона
- **GIVEN** тот же логический repo разрешён на другой машине в иной каталог
- **WHEN** строится граф на одинаковых объявлениях
- **THEN** структурные id не меняются из-за абсолютного размещения клона

#### Scenario: Разделитель в частях имени не создаёт коллизию id
<!-- F-42 -->
- **GIVEN** допустимы логические пары repo=api/x,module=m и repo=api,module=x/m
- **WHEN** строятся структурные id
- **THEN** кодирование частей однозначно, id двух модулей различны, исходные имена сохранены отдельно

### Requirement: Явная реализация и зависимости сохраняют происхождение
Явная аннотация SHALL связывать требование с названным модулем либо модулем явно названного файла; одно требование может иметь несколько модулей. Граф SHALL сохранять объявленные направленные зависимости модулей и место источника каждой связи. Улика или вычисленный кандидат MUST NOT автоматически считаться подтверждённой реализацией; смысл утверждения автора граф не доказывает (F-19, F-20, F-34, F-35).

#### Scenario: Сквозная реализация
- **GIVEN** аннотация требования называет модули core/a и plugin/b
- **WHEN** собран граф
- **THEN** оба модуля связаны с одним требованием; у связей указано место аннотации

#### Scenario: Улика о старом коде
- **GIVEN** запись журнала ссылается на файл, который изучали, но аннотации реализации нет
- **WHEN** собран граф
- **THEN** одна улика не создаёт подтверждённую связь реализации

#### Scenario: Зависимость не означает реализацию
- **GIVEN** модуль a объявляет зависимость на b, но требование явно называет только a
- **WHEN** собран граф
- **THEN** зависимость a → b сохранена; b не становится реализацией требования лишь по этой зависимости

#### Scenario: Модуль и приписанный ему файл противоречат друг другу
<!-- F-43 -->
- **GIVEN** одна декларация приписывает модулю a файл, ближайшая объявленная граница которого — модуль b, и есть независимая корректная декларация
- **WHEN** строятся связи реализации
- **THEN** противоречивая пара даёт сигнал и не связывается по догадке; независимая корректная декларация сохраняется

### Requirement: Файловые узлы ограничены используемой трассировкой
Граф SHALL создавать файловые узлы для явно названных файлов реализации и используемых источников связей и объявлений. Для файлов внутри модулей SHALL сохраняться принадлежность ближайшей границе. Остальные исходники не перечисляются только ради полного файлового индекса; происхождение ссылки на файл вне границ не заменяется выдуманным модулем (F-02, F-18, F-33).

#### Scenario: Неназванный исходник
- **GIVEN** модуль содержит README, явно названный main.py и не участвующий в трассировке helper.py
- **WHEN** собран граф
- **THEN** модуль и используемые файлы представлены, helper.py не добавлен только из-за наличия в дереве

### Requirement: Модуль без локальной связи не получает глобальную оценку покрытия
Граф и отчёт MUST NOT объявлять модуль нереализованным или не имеющим требований во всей системе только из-за отсутствия связи с требованием в данном change. Отсутствие локальной аннотации не является глобальной оценкой покрытия; объявленный модуль остаётся в структуре (F-45).

#### Scenario: Независимый модуль не объявлен нереализованным
<!-- F-45 -->
- **GIVEN** repo содержит модули a и b, а требование данного change явно связано только с a
- **WHEN** собраны граф и отчёт
- **THEN** тест отчёта подтверждает наличие b в структуре и отсутствие глобальной оценки «нереализован» или «нет требований во всей системе» только из-за отсутствия локальной связи

## MODIFIED Requirements

### Requirement: Граф собирается из файлов изменения
Скрипт trace_graph.py SHALL собирать граф на любом шаге из файлов изменения и текущих структурных объявлений участвующих repo. Напрямую граф SHALL NOT править никто: связь меняется только через её исходный файл. Без структурных объявлений сохраняется сборка существующих артефактов; источники модуля не ограничены каталогом изменения (F-05, F-16, F-18, F-26, F-30).

#### Scenario: Только что созданное изменение
- **GIVEN** изменение, где есть только `.openspec.yaml`
- **WHEN** скрипт собирает граф
- **THEN** граф пуст, код 0

#### Scenario: Граф растёт вместе с артефактами
- **GIVEN** изменение с журналом, граф несёт только записи
- **WHEN** появляется `specs/<capability>/spec.md` и скрипт собирает граф снова
- **THEN** в графе есть требования и сценарии этого файла, отдельного шага наполнения не было

#### Scenario: Связь правится через файл
- **GIVEN** требование с ``(F-19)``, в графе есть его связь с ``rec:F-19``
- **WHEN** в тексте требования номер заменён на ``(F-20)`` и скрипт собирает граф снова
- **THEN** в графе есть связь с ``rec:F-20``, а связи с ``rec:F-19`` нет

#### Scenario: Журнал не разбирается
<!-- trace-graph/F-80 -->
- **GIVEN** `decisions.json` с синтаксической ошибкой
- **WHEN** скрипт собирает граф
- **THEN** графа нет, код ненулевой, сообщение называет файл

#### Scenario: Журнал негоден по схеме
<!-- trace-graph/F-125 -->
- **GIVEN** `decisions.json` разбирается, но негоден по схеме
- **WHEN** скрипт собирает граф
- **THEN** графа нет, код ненулевой, строки называют записи, как у `check`

#### Scenario: Внешний README изменился
- **GIVEN** изменение ссылается на доступный repo с модулем
- **WHEN** объявление README изменено и граф собран снова
- **THEN** живая структура отражает новое объявление без ручной правки req-graph.json

### Requirement: Id читаемы, файл несёт версию формата
Узлы SHALL сохранять формы id: `req:capability/имя`, `scn:capability/требование/имя`, `rec:F-NN`, `task:N.M`, `cap:имя`, `sec:<текст пункта>`, `branch:<путь>:<строка>`. Модуль в id требования не входит. Новый граф SHALL нести format: 3 и source кандидата; format: 2 читается без структурных обещаний. Неподдерживаемая версия даёт сигнал с полученным и поддерживаемыми номерами; архивы формата 1 автоматически не пересобираются (F-14, F-23).

#### Scenario: Одно имя в двух capability
- **GIVEN** требование с одним именем в двух capability
- **WHEN** скрипт собирает граф
- **THEN** это два узла с разными id

#### Scenario: Переименование меняет id
- **GIVEN** требование переименовано в спеке
- **WHEN** скрипт собирает граф
- **THEN** узел несёт новый id, старого в графе нет

#### Scenario: Две ветки одного механизма
- **GIVEN** две ветки одного механизма на разных строках файла
- **WHEN** скрипт собирает граф
- **THEN** это два узла `branch:` с разными id

#### Scenario: Снимок прежнего формата
- **GIVEN** `graph/req-graph.json` с `format: 1`
- **WHEN** идёт проверка файла графа
- **THEN** строка называет полученный формат 1 и поддерживаемые форматы 2 и 3, код выхода прежний

#### Scenario: Прежний поддерживаемый файл
- **GIVEN** сохранён граф формата 2 без структурных данных
- **WHEN** новый читатель проверяет файл
- **THEN** версия принимается как прежняя; отсутствующие структурные сведения не выдаются за проверенную пустую структуру

#### Scenario: Перенос модуля не меняет требование
- **GIVEN** модуль перенесён в другой каталог без переименования требования
- **WHEN** граф собран снова
- **THEN** id требования не изменился из-за расположения модуля
