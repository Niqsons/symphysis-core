# symphysis-edge-probe

Проба краёв: требования `spec.md` → восемь категорий краёв на каждое → строки файла
покрытия и кандидаты в журнал → слово человека → сценарии в `spec.md`. Край — конкретные
данные, о которых требование молчит; кандидат — запись-развилка на один такой край
с четырьмя исходами, не черновик артефакта.

## Вход

- До первого изменяющего действия модель MUST выполнить `symphysis preflight --change <имя>`;
  селекторы `--project` и `--store`, если нужны, стоят перед подкомандой и одинаковы
  у всех вызовов. Отказ preflight или получения ресурса — остановка без записи файлов.
- Ссылки вида `symphysis resource ...` — команды: модель MUST прочитать их вывод
  целиком; это инструкции выбранной поставки, а не пути внутри store.
- `<каталог изменения>` — `openspec/changes/<имя>/`; термины — `symphysis resource doc terms.md`.
- Требования — `<каталог изменения>/specs/<capability>/spec.md`; журнал —
  `<каталог изменения>/decisions.json`, тот же, что вёл брейншторм: кандидаты получают
  следующие номера `F-NN`.
- Состав (включена ли проба) — `symphysis resource doc config.md`, часть «проба краёв».
- Форма записи-кандидата, правило рекомендации, зеркало исхода —
  `symphysis resource doc candidate.md`; команды и коды `journal.py` — `symphysis resource doc journal-cli.md`.
- Шаблон следа — комментарий «проба краёв» в `symphysis resource template spec.md`.
- У водителя — brief (раздел «Водитель»).

## Выход

- `<каталог изменения>/edge-probe.md` — файл покрытия: по строке на пару «требование ×
  категория», восемь строк на требование.
- Кандидаты в `decisions.json`; после слова человека — `outcome` у каждого и сценарии
  в `spec.md` по исходу `Specify`.
- След в конце блока каждого требования `spec.md`; строка итога в `notes[]`.
- Человеку или в отчёт водителя: кандидаты номерами, путь файла покрытия, счёт
  строк `не выбран`.

## Инварианты

1. **Решает человек, не модель.** Модель называет форму, проходит категории и пишет
   кандидата с четырьмя вариантами; исход MUST появляться только из слова человека:
   `decision` пишет `apply`, `outcome` — его зеркало; иначе край закрыт тем, кто его
   не видел.
2. **Слово нужно у выбора мимо рекомендации, не у отказа.** Рекомендованный вариант
   человек выбирает без слова: причина уже стоит в `why`; выбор мимо рекомендации без слова
   даёт сигнал `check`, страница просит слово, внести запись это не мешает. Модель
   MUST NOT требовать объяснения отказа: отказ с готовой причиной в `why` — не молчание.
3. **Каждая пара получает строку.** На требование — восемь строк файла покрытия, по одной на
   категорию; скрипт этот файл не разбирает, счёт MUST держать модель: без строки «не нашли»,
   «нашли, но не вынесли» и «не смотрели» неразличимы, и пропущенный край — отказ мимо
   человека.
4. **Край — конкретный, не напоминание.** «Подумать о границах» — не кандидат;
   «R2 сливает интервалы — что с `[[1,2],[2,3]]`, которые только касаются?» — кандидат.
   Нечего подставить в требование — это напоминание, край ещё не найден, кандидата
   MUST NOT быть.
5. **Проба стоит до кода.** Проверяющий видит только записанные утверждения и на краях,
   которых спека не назвала, уверенно ошибается; лечится не проверяющим, а полнотой спеки:
   край MUST стать сценарием до того, как появился код.

## Порядок

Сквозной пример — требование capability `busy-report`, формы `collection` и `stateful`:

```markdown
### Requirement: Отчёт сливает интервалы занятости
Система SHALL сливать пересекающиеся интервалы занятости сотрудника и записывать итог в файл отчёта.

#### Scenario: Пересекающиеся интервалы
- **GIVEN** интервалы `[[1,3],[2,4]]`
- **WHEN** собирается отчёт
- **THEN** в файле отчёта один интервал `[1,4]`

#### Scenario: Одна сборка за раз
- **GIVEN** сборка отчёта уже идёт
- **WHEN** запускается вторая сборка
- **THEN** вторая завершается отказом, файл отчёта не тронут
```

### 1. Узнай состав

Вызов скрипта состава и правила — `symphysis resource doc config.md`. Пробе нужна часть
«проба краёв»: `вкл` — такт 2; `выкл` — такт 11, и на этом проба кончается.

### 2. Возьми требования

- В счёт идут `### Requirement:` из секций `## ADDED Requirements` и `## MODIFIED
  Requirements` всех `specs/**/spec.md` изменения. Снятые и переименованные
  (`## REMOVED Requirements`, `## RENAMED Requirements`) строк и кандидатов не получают:
  поведения, которое можно уточнить, у них нет.
- Если таких требований нет вовсе — в файле покрытия заголовок и строка `требований
  в счёте нет`, кандидатов нет.
- Если `spec.md` ещё нет (скилл позван раньше) — вход: решённые записи журнала, у которых
  `consequences` называет поведение.
- Ключ требования — `<capability>/<имя требования>`: capability — имя каталога под `specs/`,
  имя — текст после `### Requirement: `. Пример: `busy-report/Отчёт сливает интервалы
  занятости`. Одно имя в двух capabilities — два требования и шестнадцать строк: без
  capability в ключе их строки слились бы.
- Требование читается как есть, на русском: перевода и cue-слов нет, форму называет модель
  по смыслу. Проба идёт по ясным требованиям: вопрос «что требование значит» — не край,
  а развилка брейншторма.

### 3. Назови форму

Пять форм, у требования одна или несколько:

| Форма | Признак |
| --- | --- |
| `numeric-range` | число с границей, порогом, округлением |
| `collection` | список, множество, интервалы, записи |
| `text` | строка: длина, равенство, нормализация |
| `stateful` | меняет состояние: запись, повтор, отмена |
| `io` | граница системы: файл, сеть, процесс, прерывание |

- Форма называется всегда и пишется в префикс вопроса записи; человек правит её там же.
- Требование о строке или числе, где нет записи, повтора, отмены, файла, сети и процесса,
  — только `text` или `numeric-range`: лишняя форма даёт лишние вопросы.
- Требованию, которому не подошла ни одна форма, — `stateful` или `io`: наблюдаемое
  поведение хотя бы меняет состояние или пересекает границу; лишнего кандидата человек
  отведёт.

### 4. Пройди восемь категорий

Каждому требованию — все восемь строк таблицы:

| id | Категория | Формы | Вопрос пробы |
| --- | --- | --- | --- |
| boundary | граничные значения | numeric-range | Что происходит ровно на каждом min/max/пороге — и на шаг в обе стороны от него? |
| adjacency | смежность / касание | collection | Когда два элемента в точности равны или только касаются — они сливаются, сталкиваются или остаются раздельными? |
| empty | пустое / вырожденное | collection, text | Каков результат на пустом, одноэлементном или null-входе? |
| encoding | кодировка / представление | text | Чьё определение длины и равенства действует — байты, кодовые точки, графемные кластеры или нормализованная форма? |
| ordering | порядок / устойчивость | collection | Когда элементы равны при сравнении, задан ли порядок вывода и устойчив ли он? |
| precision | точность / переполнение | numeric-range | Где возможны потеря точности, переполнение, округление и разрешение «ровно половины» — и каков точный контракт (half-up или half-to-even, ceil/floor/truncate)? |
| idempotency | идемпотентность / повтор | stateful | Что будет, если выполнить это дважды на одном входе? |
| concurrency | параллельность / порядок эффектов | stateful, io | Что гарантировано при прерывании или параллельном запуске? |

- Фильтр применимости: категория применима, когда её формы пересекаются с формами
  требования; требование только о тексте про переполнение не спрашивают. Девятой категории
  нет: восемь, которые автор обязан закрыть, лучше тридцати, которые никто не доходит.
- Применимой категории модель MUST задать вопрос таблицы о данных этого требования
  и искать один конкретный край. Нашлось два — берётся тот, что тише портит результат.
- Край, уже решённый в журнале (аналитик отказов брейншторма или прежняя проба), второй
  раз не поднимается: признак — запись с тем же префиксом `[категория · форма]`, называющая
  то же требование; в строке покрытия и в следе идёт её номер.

### 5. Выбери значение строки

У строки покрытия одно из четырёх значений; выбирается по порядку, первое подошедшее:

1. Категория не применима к формам требования — `неприменимо: <причина>`.
2. Вопрос задан, конкретного края нет — `не найдено: <что проверялось>`.
3. Край конкретный, но исход уже определён, и ответ человека ничего не изменит —
   `не выбран: <край>; <причина>`.
4. Край конкретный, и от ответа человека зависит, что система сделает на нём —
   `кандидат F-NN`, запись по такту 6.

Сомнение между третьим и четвёртым MUST решаться в сторону кандидата: лишнего кандидата
человек отведёт, а край, ошибочно оставленный `не выбран`, — отказ мимо человека.

Разбор на примере:

- **`кандидат F-NN`** — край ушёл человеку, в строке номер записи журнала. Категория
  `adjacency`: интервалы `[[1,2],[2,3]]` только касаются; сливать ли их в `[1,3]`,
  требование не говорит, сценарии тоже, а от ответа зависит число интервалов в отчёте.
  Строка — `adjacency · кандидат F-41`. Категория `empty`: пустой список интервалов; что
  будет в файле, тоже не сказано. Строка — `empty · кандидат F-42`. Кандидатом край
  остаётся и тогда, когда рекомендация к нему — `Dismiss` (такт 6).
- **`не выбран: <край>; <причина>`** — край найден и не вынесен, записи журнала нет, край
  и причина остаются в файле покрытия. Категория `concurrency`: две сборки одновременно;
  исход уже назван сценарием «Одна сборка за раз». Строка — `concurrency · не выбран: две
  сборки одновременно; исход уже назван сценарием «Одна сборка за раз», ответ человека его
  не изменит`. Причина — об этом крае: «неважно» и «маловероятно» не причины. Каждая такая
  строка считается в итоге пробы (такт 10).
- **`не найдено: <что проверялось>`** — категория применима, край искали и не нашли; хвост
  называет, что проверялось, иначе строку не отличить от «не смотрел». Категория `ordering`:
  равные на выходе; интервалы с равным началом пересекаются и сливаются в один, равных на
  выходе не остаётся. Строка — `ordering · не найдено: порядок равных на выходе — интервалы
  с равным началом сливаются в один, равных не остаётся`. Голое `не найдено` без хвоста
  не годится.
- **`неприменимо: <причина>`** — формы требования не пересекаются с формами категории; вопрос
  таблицы не задаётся. Категория `boundary`: формы `collection`, `stateful`, а она только для
  `numeric-range`. Строка — `boundary · неприменимо: формы collection, stateful; boundary
  только для numeric-range`. У применимой категории этого значения не бывает.

### 6. Запиши кандидата

Запись — по `symphysis resource doc candidate.md`; особенное для пробы краёв:

- `question` — `[<id категории> · <форма>] <имя требования>: <конкретный край>`: префикс —
  поле формы, которое человек может переписать; край — один, с данными этого требования;
  вопрос таблицы — подсказка модели, не текст записи.
- `options[]` — четыре, токены дословно:
  - `A. Specify — <сценарий в одну строку, который появится в spec.md: GIVEN … WHEN … THEN …>; цена: <сценарий, какой тест, сопровождение чего>`
  - `B. Dismiss — <что именно не покрывается и почему это допустимо для этого требования>`
  - `C. Backstop — <какой тест-страховка: что подаёт и что утверждает; строки в spec.md нет>`
  - `D. Defer — <что остаётся открытым и до какого события или решения>`
- `recommendation` — по правилу `candidate.md`: `Specify` при тихой порче или
  необратимости, с черновиком сценария; край известен, а в прозу не ложится — `Backstop`;
  остальное — `Dismiss` с готовой причиной; `Defer` не рекомендуется.
- `depends_on` — записи, на которых стоит требование.

Кандидат на примере:

```text
question: [adjacency · collection] Отчёт сливает интервалы занятости: `[[1,2],[2,3]]` только касаются — сливать в `[1,3]` или оставить два интервала?
A. Specify — GIVEN интервалы `[[1,2],[2,3]]` WHEN собирается отчёт THEN в файле один интервал `[1,3]`; цена: сценарий, тест на касание, правка сценария при смене правила слияния
B. Dismiss — касание не покрывается; допустимо, пока отчёт показывают только суммой часов, а она при обоих ответах одна
C. Backstop — тест подаёт `[[1,2],[2,3]]` и утверждает, что сумма часов в отчёте равна 2 при любом числе интервалов; строки в spec.md нет
D. Defer — правило касания остаётся открытым до решения, считается ли пересменка одним блоком занятости; пока tasks считает, что касающиеся интервалы не сливаются
recommendation: A — в файле то один интервал, то два, и ошибку никто не заметит сразу: отчёт выглядит верным; цена — сценарий и тест на касание
```

Второй кандидат того же требования, `[empty · collection]`: пустой список интервалов даёт
пустой файл отчёта, человек видит это сразу, и ничего не портится. Рекомендация — B, причина
в `why`; вариант A всё равно есть и называет цену.

После каждой записи — `check`, затем `render-md`.

### 7. Запиши файл покрытия

Когда все кандидаты в журнале — файл `<каталог изменения>/edge-probe.md`: заголовок и по
строке на пару, в порядке таблицы категорий, требования подряд. Форма строки —
`- <ключ требования> · <id категории> · <значение>`, одна строка файла на пару. Файл
покрытия целиком на примере:

```text
# Покрытие пробы краёв: busy-report-merge

- busy-report/Отчёт сливает интервалы занятости · boundary · неприменимо: формы collection, stateful; boundary только для numeric-range
- busy-report/Отчёт сливает интервалы занятости · adjacency · кандидат F-41
- busy-report/Отчёт сливает интервалы занятости · empty · кандидат F-42
- busy-report/Отчёт сливает интервалы занятости · encoding · неприменимо: формы collection, stateful; encoding только для text
- busy-report/Отчёт сливает интервалы занятости · ordering · не найдено: порядок равных на выходе — интервалы с равным началом сливаются в один, равных не остаётся
- busy-report/Отчёт сливает интервалы занятости · precision · неприменимо: формы collection, stateful; precision только для numeric-range
- busy-report/Отчёт сливает интервалы занятости · idempotency · не найдено: вторая сборка на тех же интервалах — итог зависит только от входа, файл перезаписывается тем же содержимым
- busy-report/Отчёт сливает интервалы занятости · concurrency · не выбран: две сборки одновременно; исход уже назван сценарием «Одна сборка за раз», ответ человека его не изменит
```

Перед закрытием модель MUST сверить счёт: строк в файле ровно восемь на требование;
`check` этот файл не разбирает, пропущенную пару никто не назовёт.

### 8. Круг просмотрщика

Когда кандидаты по всем требованиям записаны — круг просмотрщика: скилл `symphysis-viewer`,
«Порядок». Особенное пробы: у `A` слово человека — строка сценария, если он задаёт её сам.
Молчаливого отказа нет: отвергнутый край остаётся в журнале с причиной в `why`.

### 9. Зеркало исхода

После `apply` у каждой записи пробы с `decision` — зеркало по `symphysis resource doc candidate.md`:
`outcome` по букве (`A → Specify, B → Dismiss, C → Backstop, D → Defer`), сценарий
в `spec.md` у `Specify` — под требованием, после последнего сценария и выше строк следа,
со строкой `<!-- F-NN -->` сразу под заголовком сценария, `consequences` по исходу. Выбор мимо рекомендации без слова — вопрос человеку по `candidate.md`.

### 10. Оставь след и итог

- След стоит в конце блока каждого требования, после всех его сценариев: выше первого
  сценария он считается в предел 500 символов текста требования, и `validate --strict`
  падает на длинном следе. Форма — комментарий шаблона `spec.md`:
  `<!-- проба краёв: форма=<формы>, исходы: F-NN Specify, F-MM Dismiss, … -->`; кандидат без
  решения пишется как `F-NN открыт`, кандидатов нет — `исходы: нет`.
- Проба закрывается строкой `notes[]`: `{date, text: «проба краёв: кандидатов N, Specify a,
  Dismiss b, Backstop c, Defer d; не выбран k: <ключи требований через запятую>»}`. `k` —
  число строк `не выбран` в файле покрытия, дальше ключи их требований, у `k = 0` —
  `не выбран 0`. Без этого счёта такой край был бы отказом, которого человек не видит:
  строка итога — единственное, что выводит его наружу. Кандидаты без решения входят в N
  и перечисляются номерами.
- Затем `render-md`, `render-html`. Открытый кандидат артефакт не блокирует: его увидят
  атака `symphysis-attack` и Open Questions дизайна.

### 11. Выключенная проба

Такт идёт вместо всех прочих, когда состав назвал `проба краёв выкл`.

- Если файла покрытия нет и кандидатов пробы в журнале нет — кандидатов не заводить, файл
  покрытия не писать; в конец блока каждого требования — `<!-- проба краёв: выключена настройкой -->`:
  без комментария выключенная проба читалась бы как пройденная. Проба запретов идёт
  независимо.
- Если прежний проход уже был (файл покрытия или записи `[<категория> · <форма>]`) — файл
  и записи остаются как есть: они несут слово человека; новых записей нет; след называет
  выключение рядом с прежними номерами:
  `<!-- проба краёв: выключена настройкой; прежний проход: форма=<формы>, исходы: F-NN Specify, … -->`.

### 12. Повтори пробу после правки требования

Проба идёт снова после правки или переименования требования.

- Файл покрытия переписывается целиком: старые строки не переносятся, строк про требования,
  которых больше нет, в нём нет.
- Кандидат сохраняет номер и решение: запись ищется по категории и требованию,
  у переименованного — по новому имени; в строке покрытия её номер, второй записи нет. Имя
  требования в `question` и `evidence[].quote` MUST быть поправлено на новое, иначе `check`
  даст «цитаты нет дословно»; `decision` и `outcome` не трогаются. Префикс, переписанный
  человеком, не возвращается.
- Снятое требование строк не получает, его запись остаётся в журнале.
- След и строка итога пишутся заново по новому файлу.

## Коды и сигналы

Коды и маркеры `journal.py` и скрипта состава — `symphysis resource doc journal-cli.md`,
`symphysis resource doc config.md`. Особенное для пробы:

- `check` код 1 после записи кандидата → поле схемы пропущено или антипод внутри одной
  развилки: исправить запись до следующей.
- `check` строка `[!!]` «цитаты нет дословно» у кандидата → в `evidence[]` не строка
  `### Requirement:` или SHALL как есть: открыть `spec.md` и взять строку дословно.
- `validate --strict` падает на требовании со следом → след стоит выше первого сценария:
  перенести в конец блока (такт 10).
- Состав `проба краёв выкл` → такт 11 вместо всех прочих.

## Границы

- Вопрос «чем это станет молча» — скилл `symphysis-prohibition-probe`; проба запретов идёт
  независимо от состава пробы краёв.
- Круг просмотрщика, слово человека, `apply` — скилл `symphysis-viewer`.
- Категорий ровно восемь, `unclassified` не поднимается; обратимость кандидата
  не оценивается — он не проектное решение.
- Тест-страховка `Backstop` — пишет `tasks`; здесь только намерение в `consequences`.
- Развилки замысла и вопрос «что требование значит» — скилл `symphysis-brainstorm`.
- Состав читает только `symphysis_config.py` (`symphysis resource doc config.md`); `symphysis.yaml`
  модель не читает и человека о составе не спрашивает.

## Приёмка

- `decision` у кандидатов — только из `apply`; `outcome.value` совпадает с буквой решения,
  `reason` — слово дословно.
- `check` без сигнала «выбран не рекомендованный вариант» либо слово получено от человека.
- В `edge-probe.md` восемь строк на каждое требование ADDED и MODIFIED, ключ
  `<capability>/<имя>`; значение из четырёх; у `не найдено` хвост, у `не выбран` край
  и причина.
- `question` каждого кандидата называет данные этого требования; вопрос таблицы дословно
  в `question` не встречается.
- Каждый текст варианта начинается своим токеном (`Specify`, `Dismiss`, `Backstop`,
  `Defer`); четыре текста попарно различны и не повторяют текст другого кандидата прогона.
- `A` или `C` рекомендованы только у края, который тихо портит результат или необратим,
  с этим в `why`; вариант `A` называет цену.
- У каждого кандидата категория из восьми и форма из пяти; категория применима к форме
  по таблице; префикс `[id · форма]` в `question`, переписанный человеком префикс моделью
  не возвращён.
- У каждого требования след «проба краёв» в конце блока, после сценариев, с формой
  и исходами по номерам; на каждый `Specify` — сценарий с `<!-- F-NN -->` под заголовком.
- Строка `notes[]` с N, a, b, c, d, числом строк `не выбран` с ключами требований и датой.
- При выключенной пробе кандидатов и файла нет, след `выключена настройкой` у каждого
  требования; прежний проход не тронут.

## Водитель

Водитель у пробы — по настройке, по умолчанию проба идёт в главной нити: без контекста
решений журнала водитель заводит лишние кандидаты (состав — `symphysis resource doc config.md`,
часть «водители»).

- Водителю идут такты 1–7 и 11: от состава до файла покрытия. Главной нити — такты 8–10:
  круг просмотрщика, зеркало исхода, след и итог; такт 12 — по слову человека.
- Brief — `<каталог изменения>/briefs/symphysis-edge-probe-<YYYY-MM-DD>/brief.md`:
  `skill: symphysis-edge-probe`, `artifact: specs`, `change: <имя>`, `config` — строка
  состава дословно, `inputs` — `specs/**/spec.md`, `decisions.json`, `report` — путь отчёта.
- Отчёт `report.md` рядом с brief: «Итог» (требований в счёте, кандидатов, строк
  `не выбран`), «Файлы» (`edge-probe.md`, номера записей), «Вопросы человеку» (края,
  где кандидат и `не выбран` спорны), «Сигналы» (строки `[!!]`, «критерий не выполнен: …»
  по «Приёмке» для тактов 1–7), «Не сделано».
- Водитель MUST NOT звать `apply`, писать `decision` и `outcome`, править `spec.md`
  и спрашивать человека.
