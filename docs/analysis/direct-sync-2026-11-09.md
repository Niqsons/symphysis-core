# Порция 3: direct sync сохраняет базу до переноса

Дата: 2026-11-09. Начальная версия ядра — `98c2b0b` (B-45).
Состав следует [согласованному разбору](fork-symphysis-flow-required-changes-2026-11-09.md), разделу «Порции и проверки», пункту 3.
После B-45 владелец разрешил следующую порцию: «можно приступать к следующей порции».
Отдельная сверка результата и координация archive — пункт 4, здесь не реализованы.

## Изменение

Обе формы workflow sync — skill и command — получают одну общую вставку из `symphysis-sync.ts`.
Существующие шесть шагов сохранены. Для `status.schemaName == symphysis` порядок теперь явный:

1. Выбрать точные дельты из inventory CLI и получить правила содержимого.
2. Найти установленный инструмент проекта вызова; до записи проверить поддержку фильтра якоризации.
3. Вызвать freeze до первой записи мастера, из `planningHome.root`, с картой корней установки,
   если она есть. Store выбирается рабочим каталогом Python-инструмента, а не флагом `--store`.
4. Перенести выбранные блоки без комментариев следов проб, сохранив прочие комментарии и происхождение ссылок.
5. Якоризировать только выбранные capabilities, показать настоящий вывод, затем валидировать мастер.

Новый отчёт графа передаётся ссылкой из вывода; свежий снимок не порождает новую ссылку.
Ошибку графа нужно показать, не заявляя о сохранённой базе; сама ошибка не становится гейтом sync/archive.
Ошибка якоризации означает незавершённый sync, который нельзя отдавать архиву как успешный.
Для других схем блоки symphysis пропускаются; Python-инструменты им не требуются.

Выявлена необходимая зависимость: старый `anchor_refs` проходил все дельты, хотя sync допускает
точный выбранный набор. Добавлен необязательный повторяемый `--capability`: без него поведение прежнее;
неизвестное имя в фильтре вызывает отказ до любой записи, дубликаты не приводят к повторным заменам.
Исключённые мастер-спеки остаются байт в байт прежними. Workflow передаёт весь выбранный набор явно.

Из `rules.specs` в конфиге ядра и образце установки убран вызов скрипта: правило задаёт форму якорей,
а операцией владеет workflow. Обновлены справка sync, GUIDE, мастер-нормы `trace-snapshot` и `record-anchors`.
Тексты новых/изменённых требований не длиннее 500 знаков даже с комментариями провенанса: 477, 467, 434.
При обновлении старого проекта инсталлятор сохраняет его прежние правила; новая строка не удаляет их автоматически.
Новый workflow по-прежнему запрещает artifact rules менять порядок операции.

Применены `writing-skill-bodies` и канон проекта: признак → действие → последствие,
именованные корни и выбранная область, явные MUST и два свежих исполнения одинакового brief.
По исключению в начале `docs/skills-canon.md` скиллы `openspec-*` не переводились на полный скелет symphysis:
сделана точечная правка исходных шаблонов, английский язык существующего тела сохранён.
Повторяемый текст двух форм вынесен в общую TS-вставку; в форке есть ссылка на канон и запись C17 в UPSTREAM.
`continue-change.ts` не менялся, B-24 этим изменением не запускается.
Разрешение инструментов рассчитано на текущую проектную установку `.symphysis/tools`;
подключение глобальной установки B-67 в эту порцию не включено.

## Модельная проверка

Три независимых запуска Terra medium: до и два после, `fork_turns: none`.
Два после получили одинаковое задание, с заменой пути собственного каталога.
Настоящий store `bench` регистрировался в изолированных XDG config/data; Git в нём не создавался.
Проект вызова и store различались; в проекте вызова был локальный мастер-приманка.
Инструменты лежали в проекте вызова, но писать следовало в planning root store.
Исполнителям разрешены только материалы собственной пробы. Это изоляция контекста/входов,
не системная песочница прав доступа.

Выбрана одна из двух дельт. Она переименовывает и меняет требование, унаследовав голый `F-20`
и добавив `F-21`; исключённый мастер тоже имеет номера, которые нельзя менять.
Успех проверен по хешам исходных файлов, содержимому мастера, базе снимка и техническому следу
вызовов с хешами мастеров на момент запуска инструмента. Обёртки задавали окружение и журналировали
вызовы, настоящие CLI и Python-скрипты выполнялись из замороженных копий.

Старый запуск сделал дополнительную изолированную копию выбранной дельты для старого якоризатора,
не сняв базу. Скрипт сообщил об отсутствии базы и переписал оба номера. Эта прямой запуск копии
обошёл журналирующую обёртку: нулевой счётчик её вызовов в локальном score не означает, что якоризатор не запускался.
Результат виден в мастере и отчёте исполнителя. Простая зелёная CLI-валидация потерю происхождения не обнаружила.

В двух новых запусках форма результата и последовательность совпали: один freeze перед записью,
один anchor с `--capability primary` после неё, валидация выбранного store. Ни один защищённый
исходный файл не изменён; перенос затронул только выбранный мастер.
Это воспроизведение одного случая, не статистическое доказательство для всех изменений.

Ещё один свежий Terra последовательно проверил две независимые ветки:

- Контрольная ошибка freeze: сообщение показано, база не заявлена, sync продолжен,

- `spec-driven` без установленного каталога Python-инструментов: специальные шаги не запускались,
  обычный перенос и валидация прошли. Ссылки и комментарий пробы сохранены по каноническому workflow.

В ветке ошибки использован уже заякоренный чужой номер. Она не доказывает защиту старого голого
номера без снимка: прежняя диагностика якоризатора прямо предупреждает, что без базы переписываются
все голые номера журнала. Контроль происхождения результата при этом исходе остаётся частью порции 4.
