# Подписи узлов задач: проверка пользовательского примера

Дата: 2026-11-09. Входы: `# Tasks.txt` и `req-graph.txt` из текущего worktree.
Владелец уточнил цель: уменьшить **подписи узлов задач**, не обязательно объём JSON.
Фактический способ просмотра — внешний Mermaid-просмотрщик. Встроенный просмотр графа
в symphysis и экспорт в форматы графовых визуализаторов — отдельные задачи.
Продуктовый код и оба входных файла при проверке не менялись.
Этот документ фиксирует первоначальный разбор. Последующая реализация, выбранный формат
и одобрение владельца — в [отчёте порции 6](task-labels-implementation-2026-11-09.md).

задачи в этой грамматике нет. В `claims` тот же текст передаётся для извлечения связей
со сценариями и записями. Это действующий разбор, закреплённый также тестом
`test_task_nodes_take_checked_and_unchecked_lines_only`.

## JSON и штатный Mermaid — разные представления

В JSON `name` содержит полное тело задачи. Просмотрщик, использующий name как видимую
подпись, получает тысячи знаков. Штатный Mermaid уже ограничивает имя блока вместе
с номером 90 знаками (`diagram_name`, строка 1197), но это обрезанное начало тела:
например номер, путь Python-файла и начало сигнатуры вместо названия действия.

На данном снимке обычный `diagram_text` отказал: 57 283 знака при пределе 50 000.
Лимит не менялся. Для диагностики отдельно вызван внутренний рендерер, чтобы измерить
представление, не объявляя успешным штатный экспорт сверх лимита.

Вторая диагностическая отрисовка меняла только подписи задач на стабильные `TASK_1.1`
и аналогичные номера. Остальные подписи, типы, docref, узлы и связи те же. Результат —
47 863 знака, на 9 420 меньше, то есть примерно на 16,4%. Смысловой короткий заголовок
в этом опыте не генерировался: номер — контрольный вариант, показывающий вклад подписей,
а не согласованное окончательное оформление. Количество узлов и связей не уменьшается.

## Почему нельзя просто обрезать name при сборке

На `name` сейчас опирается не только изображение. `service_tasks` и проверка «задача
ни к чему» ищут точную хвостовую пометку `служебная` в полном тексте. В данном снимке
таких задач восемь. При диагностической замене name на короткий номер их стало ноль.
Это воспроизведено на копии структуры в памяти, без изменения сохранённого графа.

Поэтому краткая видимая подпись должна быть отделена от текста, нужного для анализа.
Ссылки на сценарии и записи надо продолжать извлекать из всей строки, включая хвост;
id `task:N.M`, done и at сохраняются. Сокращение структуры канонического графа — отдельное
изменение контракта данных, для цели владельца сейчас не требуется.

## Предлагаемая отдельная порция

Включить в fork-symphysis-flow соседнюю порцию **«компактные подписи задач в Mermaid»**.
Она связана с удобством просмотра замороженного графа; корректность sync/archive
не должна ждать её реализации, и размер подписи не становится новым гейтом архивации.

Граница порции:

- Сделать отдельное правило короткой подписи для task. Надёжный fallback для старых
  задач — номер, без попытки угадать смысл длинного кода или обрезанной фразы.
- Если нужен смысловой заголовок, рассмотреть явное короткое название при написании
  новых tasks на той же checkbox-строке. Это дополнительное решение по instruction и
  шаблону tasks; существующие файлы не переписываются массово.
- Полное тело оставить в канонических данных для анализа; исходная строка остаётся
  доступной по at/docref. Подробный просмотр в интерфейсе symphysis этим не реализуется.
- Короткую подпись формировать в Mermaid-экспорте, на этапе отображения. Ради этой
  порции не менять name канонического JSON, не добавлять новое поле и не мигрировать снимки.
- Окончательная форма короткого заголовка ещё не выбрана. Новый обязательный формат tasks
  этим разбором не вводится. Внедрение просмотра в symphysis и отдельный экспорт для
  графовых визуализаторов, включая B-05, остаются за пределами данной порции.

Приёмка: короткая подпись не содержит тело проверки; длинная задача со ссылками в конце
сохраняет все связи; восемь служебных задач примера остаются служебными; checkbox, id и at
не меняются; одинаковые начала разных задач не сливают узлы; старый format 2 экспортируется
в Mermaid без миграции. Проверять нужно фактические подписи Mermaid-просмотрщика,
а не только количество символов файла.
