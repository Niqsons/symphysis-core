## 1. Вызов

**Наблюдено.**

- Имя: `export const name = "subagent"` (`packages/core/src/tool/plugin/subagent.ts:17`). Старые имена переименованы: «`bash` is now `shell`; `task` is now `subagent`; `apply_patch` is now `patch`» (`packages/core/test/v1-migration.test.ts:512`).
- Поля: `agent`, `description`, `prompt`, `model`, `sessionID`, `background` (`subagent.ts:30-48`). Вхождения `task_id` и `subagent_type` в `packages/core/src` остались только в миграции базы (`src/database/v1-migration.bun.ts`).
- Новый ребёнок начинает с нуля: «New child sessions start with fresh context, so include all relevant context and instructions when you don't pass a sessionID» (`subagent.ts:58`).
- Агент режима `primary` субагентом не становится: `Agent ${input.agent} cannot run as a subagent` (`subagent.ts:142-143`).
- Модель: `override ?? agent.model ?? parent.model` (`subagent.ts:190`).

## 2. Сессии

**Наблюдено.**

- Продолжение: «Send a follow-up to an existing subagent, running or finished. Omit to start a new one» (`subagent.ts:42`).
- Неизвестный id: `Subagent session not found` (`subagent.ts:162-169`). Чужой: `is not a child of the current session` (`subagent.ts:170-173`).
- Продолжение с другим `agent` **меняет агента в сессии**: `sessions.switchAgent` (`subagent.ts:177-187`).
- Фон: `background: true` сразу возвращает управление, о конце приходит уведомление. Текст инструмента: «DO NOT sleep, poll for progress, ask the subagent for status, or duplicate this subagent's work» (`subagent.ts:19-28`).
- Каталог ребёнка: `const location = parent?.location ?? ...` (`packages/core/src/session.ts:294`). Параметра каталога у `subagent` нет.

**Вывод.** Записанный отказ «`task_id` с неизвестным id молча даёт чистую сессию» на 2.2.5 не воспроизводится по коду, разбор надо поправить. Новый риск той же породы: продолжение с другим именем агента молча меняет исполнителя, а это отказ «подмена исполнителя» из раздела 3 разбора. Тело диспетчера должно продолжать только с тем же `agent`.

## 3. Глубина

**Наблюдено.**

- Проверка: `Config.latest(yield* config.entries(), "experimental")?.subagent_depth ?? 1`, затем отказ при `depth >= limit` (`subagent.ts:135-139`). Глубина — число предков текущей сессии (`subagent.ts:123-134`).
- Значит, при умолчании главная сессия зовёт субагента, а субагент субагента — уже нет: `Subagent depth limit reached (1)`.
- Схема: `subagent_depth` в `experimental`, «Maximum subagent nesting depth. Defaults to 1» (`packages/schema/src/config/experimental.ts:43-45`).
- **Документация расходится с кодом.** `packages/web/src/content/docs/config.mdx:550-559` показывает ключ верхнего уровня, а `packages/core/src/config/normalize.ts:45` числит его в `unsupportedTopLevel`, и он отбрасывается с диагностикой «omitted unsupported legacy setting» (`normalize.ts:874-876`).

**Вывод.** Для формы «агент главной нити, исполнители, никого дальше» настройка не нужна: хватает умолчания 1. Это совпадает с Claude Code по смыслу, хотя там предел другой: три слоя, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`. Запрет порождать дальше у Claude Code держится снятием `Agent` у исполнителя, а у opencode — самим пределом.

## 4. Ограды

**Наблюдено.**

- Родной вид в шапке: `mode`, `hidden`, `steps`, `disabled`, `permissions` и другие (`packages/schema/src/config/agent.ts:16-25`), правило — `{ action, resource, effect }` (`packages/core/test/config/normalization.test.ts:294`).
- Старый вид мигрирует: `task` в `subagent`, `bash` в `shell`, `write` и `apply_patch` в `edit` (`packages/core/test/config/config.test.ts:1476-1494`). Шапка файла идёт через миграцию, только если в ней есть неизвестный ключ и нет родных; при смеси неизвестные ключи только дают предупреждение «ignored unsupported agent fields» (`packages/core/src/config/plugin/agent.ts:188-208`).
- Право на запуск проверяется действием `subagent` по имени агента, отказ: `Subagent denied` (`subagent.ts:144-157`). Запрещённые и скрытые агенты убираются из списка в описании инструмента (`subagent.ts:294-300`).
- Порядок: «the **last matching rule winning**» (`packages/web/src/content/docs/permissions.mdx:92`). Документация ещё называет ключ `task` (там же, `:160`).
- Пути и команды разбираются по-разному: «Expand only resources tools resolve as filesystem paths. Bash resources are raw shell text» (`agent.ts:141-142`).

**Вывод.** Ограда `dispatch.md` формально переживёт переход, но это держится на миграции и на отсутствии родных ключей в шапке: одна родная строка рядом со старой, и старые права будут проигнорированы с предупреждением в журнал. Новый диспетчер писать сразу родным видом.

## 5. Параллельность и worktree: два клиента

| Что | Claude Code | opencode 2.2.5 |
| --- | --- | --- |
| Запуск нескольких | «spawn multiple subagents to work simultaneously»; предел 20, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` | `background: true`; два вызова одним ответом тоже идут одновременно (проба), но оба в каталоге родителя; предела в прочитанном коде нет |
| Worktree на исполнителя | `isolation: worktree` в шапке | параметра нет, ребёнок в каталоге родителя (`session.ts:294`) |
| Замена | | `worktree_create` и `session_move` (`packages/core/src/tool/plugin/opencode.ts:137-175`); рабочая связка — раздел 7 |
| База worktree | по умолчанию **ветка по умолчанию на удалённом**, не текущая | текущий `HEAD` основного клона, ловушки нет (проба); дерево на `detached HEAD`, ветки нет |
| Запись вне своего дерева | заблокирована клиентом для `Edit`, `Write`; у PowerShell только проверка каталога | `external_directory`, по умолчанию `ask` |
| Что не попадёт в worktree | игнорируемые файлы, если не названы в `.worktreeinclude` | незакоммиченное не попадает (проба); игнорируемые не смотрел |

**Наблюдено, Claude Code, страница `worktrees`.**

- База: «`"fresh"` (default): branch from the repository's default branch on the remote»; «`"head"`: branch from your current local `HEAD`... Use this when isolating subagents that need to operate on in-progress work». Имя ветки задать нельзя.
- Без удалённого: «the worktree falls back to your current local `HEAD`».
- Ограда: «Claude Code blocks an `Edit`, `Write`, or `NotebookEdit` that targets a path in the main checkout». Но «None of them tracks which files a shell command writes» и «For PowerShell commands, Claude Code applies only the working-directory check».
- Инструкции: «A subagent in its own worktree takes the instruction files it starts with from your main conversation, not from its worktree».
- Скиллы: в worktree без своего `.claude/skills` «Claude Code loads the main checkout's project skills», то же для `.claude/agents` и `.claude/commands`; для скиллов нужен v2.1.277 или новее.
- Что возвращает субагент из worktree (путь, ветка), в прочитанном не описано.

**Вывод.**

1. **Самая опасная находка — база по умолчанию.** Без `worktree.baseRef: "head"` исполнитель стартует от ветки по умолчанию и не видит ни рабочую ветку, ни прошлые группы. Сообщения нет. Хуже того, в репозитории без удалённого всё работает верно, поэтому проба на временном репозитории дефект не покажет. «а корпоративном контуре почти всегда есть remote. правда надо понять, что является базой? ветка и коммит, в которых открыт проект на момент spawn агента?» (ce91:F3). Ответ — ниже, в таблице пробы.
2. Даже с `"head"` worktree содержит только закоммиченное. План должен быть в коммите до раздачи, а `.symphysis/tools` и другие игнорируемые файлы — в `.worktreeinclude`, если они нужны исполнителю.
3. По правилу из F3 ограда по пути в шапке отпадает: она есть у opencode и нет у Claude Code. Цена снята: «внутри своего дерева править всё -- нормально, так как относительно безопасно.» (ce91:F4). Запись в основной клон блокирует `isolation: worktree`.
4. Обратный случай правило из F3 не называет: `isolation: worktree` есть у Claude Code, а у opencode его нет, хотя F18 называет её очень удобной. Решено вариантом Б1 разбора диспетчера: на Claude Code она, на opencode замена из раздела 7, проба её подтвердила.

**Наблюдено, проба Claude Code 2.1.317** на временном репозитории с настоящим удалённым. Показания взяты из журнала команды субагента и из git, а не из доклада модели.

| Что проверено | Результат |
| --- | --- |
| Сессия на `feat` с незакоммиченной правкой, настройки нет | база — `origin/HEAD`; коммита `feat` и его файла в worktree нет |
| `worktree.baseRef: "head"` | база — коммит `feat`, на котором стоит основной клон |
| Родитель коммитит прямо перед вызовом субагента | база — этот новый коммит: **HEAD в момент запуска субагента, а не начала сессии** |
| Незакоммиченная правка, неотслеживаемый и игнорируемый файлы родителя | в worktree не попадают |
| Ветка исполнителя | новая, `worktree-agent-` плюс идентификатор, от базы |
| Что получает родитель | при изменениях `worktreePath` и `worktreeBranch`; без изменений этих полей нет и worktree удалён |
| Два субагента одним сообщением из `claude --agent` со списком `Agent(writer)` | идут одновременно: интервалы работы пересеклись |
| Передний план или фон | **выбирает модель**: одни вызовы пришли с `run_in_background: false`, другие сразу вернули `async_launched` без результата |
| Вливание веток git-ом в рабочую ветку | прошло, незакоммиченная правка родителя цела |

Итог по ce91:F3: при `head` база — да, ветка и коммит основного клона на момент запуска агента. Без настройки — удалённая ветка по умолчанию, и в корпоративном контуре с удалённым это сработает всегда.

Вывод: тело диспетчера должно задавать фон или передний план явно, иначе он то получит результат, то нет.

## 7. Worktree на opencode: проба

«нужно проверить. иначе дальше не сможем проектировать.» (ce91:F7).

**Запущено 2026-11-03** на установленном 2.2.5: `client-probe-opencode-worktree-2026-11-03.txt`, скрипт рядом. Вместо модели локальная заглушка, домашний каталог и `TEMP` подменены, настоящие каталоги opencode не изменились. Поэтому проба отвечает на вопрос «что делает клиент», а не «как модель исполнит тело».

| Вариант | Что показала проба | Вывод |
| --- | --- | --- |
| Родитель двигает ребёнка: `subagent` в фоне, затем `session_move` с его `sessionID` | первый ход ребёнка всегда в общем каталоге, даже когда перемещение пришло за 4 с до ответа модели. При гонке второй ход тоже: **файл молча записан в основной клон** | нельзя |
| Ребёнок двигается сам первым ходом | все следующие ходы и файл в дереве | работает, но держится текстом тела |
| Родитель входит в дерево перед запуском: свой `session_move`, затем `subagent` в фоне; для второго дерева повторить | каждый ребёнок с первого хода в своём дереве, файлы на месте | **рекомендую**: порядок держит родитель, тексту исполнителя верить не надо |
| Без перемещения: абсолютные пути и `workdir` | работает при `external_directory: allow` | держится на каждом вызове модели |

**Весь путь, сценарий `pipeline`:** основной клон на `feat`, есть удалённый и незакоммиченная правка. База дерева — текущий коммит `feat`. Коммит в дереве прошёл. Вливание по хешу в `feat` прошло, правка родителя цела.

Отличия от Claude Code, которые должно знать тело диспетчера:

- Дерево на `detached HEAD`, ветки нет: хеш коммита нужно взять из отчёта исполнителя или из `git worktree list`.
- Дерево лежит в каталоге данных opencode, а не в проекте.
- `worktree_create` и `session_move` вызываются через `execute` кодом `tools.opencode.session_move(...)` (`packages/core/src/tool/AGENTS.md:33`, `packages/core/test/tool-opencode.test.ts:91`). Форму надо дать в теле дословно.
- Два `subagent` одним ответом идут одновременно, но оба в каталоге родителя, поэтому для партии с деревьями нужен фон и запуск по очереди.

**Находка про оболочку.** Порядок выбора на Windows: `pwsh`, `powershell`, Git Bash, `cmd` (`packages/core/src/shell/select.ts:99-102`). В пробе досталась Windows PowerShell 5: `&&` там ошибка, а её текст пришёл нечитаемым в неверной кодировке. Тело исполнителя и команды проверки не должны полагаться на `&&`; какая оболочка будет на настоящем окружении, посмотреть на замере.

## 8. Зависание провайдера

Проба и код opencode (таймауты сокращены до 3–5 с):

| Что делает провайдер | Что произошло |
| --- | --- |
| Молчит, нет даже заголовков | 4 попытки, затем родитель получает `state="error"`: «Timed out waiting for response headers» |
| Длинная очередь: заголовки есть, идут только служебные комментарии | за 60 с одна попытка, таймаута нет, **родитель не узнаёт ничего**: комментарии сбрасывают `chunkTimeout` |
| Та же очередь, но задан общий `timeout` провайдера | 4 попытки, затем `state="error"`: «Timed out waiting for the response to complete» |

В коде: `headerTimeout` 5 минут и `chunkTimeout` 15 минут по умолчанию, у `timeout` умолчания нет (`packages/core/src/provider.ts:231`, `:238`, `:245-250`); запрос, упавший по таймауту, повторяется не больше трёх раз (`packages/core/src/model-retry.ts:40`). Значит, при немом провайдере без настройки родитель узнает об отказе примерно через 20 минут, при оборвавшемся потоке примерно через час; это мой подсчёт. Ошибка родителю приходит на его следующем ходу. Комментарии я имитировал сам: шлёт ли их настоящая очередь, зависит от хоста.

**Наблюдено, Claude Code, страница `workflows`.** Есть окно молчания `CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS`, «which also applies to subagents outside workflows», и сторож потока `CLAUDE_STREAM_IDLE_TIMEOUT_MS`. Значений по умолчанию в прочитанном нет, живьём не смотрел. В workflow зависший агент перезапускается сам, до пяти раз.

**Вывод.** Замечание ce91:F5 подтверждено: при очереди со служебными комментариями на opencode конца может не быть вообще. Правило «без наблюденных отказов неизвестно что сторожить» его не отменяет, потому что отказ наблюдён: `dispatch.md:184`, «Зависший неотличим от работающего». Самый дешёвый кандидат: общий `timeout` провайдера плюс строка в теле диспетчера о сроке, после которого идти к человеку. Цена `timeout`: он оборвёт и честно долгий ответ, значит, значение должно быть больше самого долгого шага. Подбирать на замере.

| Механизм | Что это | Годится ли, вывод |
