# Контракт связанных репозиториев

Действует для ядра `symphysis` и плагина symphysis на трёх платформах. VS Code — основная: функциональность плагина сперва появляется и проверяется в `symphysis-vscode`. GIGA IDE и opencode — порты: `symphysis-giga` и `symphysis-opencode` следуют за функциями плагина VS Code и держат свои файлы сборки. Сказанное ниже о плагине относится к каждому из трёх, если не назван плагин VS Code. На другие репозитории контракт не распространяется, у них свои правила пуша.

## Раскладка

| Что | Где |
| --- | --- |
| схема, скиллы, инструменты журнала, страница, инсталлятор | `symphysis`, удалённый `Niqsons/symphysis-core` |
| плагин VS Code, основная платформа | `symphysis-vscode`, удалённый `Niqsons/symphysis-vscode` |
| плагин GIGA IDE, порт | `symphysis-giga`, удалённый `Niqsons/symphysis-giga` |
| плагин opencode, порт | `symphysis-opencode`, удалённый `Niqsons/symphysis-opencode` |
| механики замера: раннеры, водитель, сборка плеч, правила судейства | `skills-factory` |
| замеры: прогоны, листы, эталон | только на диске |
| копии исходников доноров, `upstream/` | не публикуются; упоминать источник в текстах можно |
| наши правки форка OpenSpec | ветка `openspec-fork` в `symphysis-core`, оставлена по слову человека |

## Подпись коммита

Коммит из работы над другим проектом несёт `Origin:` с проектом и веткой и `Why:` с причиной для той стороны. Родной коммит подписи не несёт. Исключение одно: коммит со сменой контракта называет её в `Why:`, даже если он родной.

```
feat(journal): view-json: данные журнала для показа вне страницы

Origin: symphysis-vscode feat/part1-viewer
Why: плагину нужны данные журнала без разбора HTML страницы
Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

Формат держат три правила, и все три нарушаются молча:

- подпись стоит в последнем абзаце сообщения, вместе с `Co-Authored-By`: отдельным абзацем git её не видит;
- `Why:` пишется в одну строку, перенос только с отступом: строка без отступа убивает всю подпись;
- имя `Origin`, а не `From`: `From:` первой строкой тела ломает `format-patch | am`.

Список подписанных коммитов и заодно проверка формата. Коммит нашёлся, а после `|` пусто: подпись сломана.

```
git log --grep='^Origin: ' --format='%h %s | %(trailers:key=Origin,valueonly,separator=)'
```

## Обратная ссылка

Коммит плагина, которому нужен коммит ядра, несёт `Needs: symphysis <хеш>` в том же абзаце.

## Что входит в контракт ядра с плагином

- грамматика строк `apply`: плагин сам пишет эти строки, и они попадают в журнал; строка о тяжести `- тяжесть: …` правит файл атаки, журнал она не меняет;
- подкоманды и аргументы `journal.py`, которые вызывает плагин, в том числе `--out`, `--attack`, `--dry-run`;
- вывод `view-json`, в нём поле `contract` с номером контракта;
- вывод `step_help.py`: поле `contract` то же самое число; поля — в `step-help/tests/test_step_help.py`, `test_output_shape`, исходы и коды — в `step_help.py --help`;
- коды выхода `journal.py`;
- значения полей, которые плагин разбирает: тяжесть, вид записи, адресат парковки и записи (`агент | человек | ИБ`), закрытие «вопрос человеку», метка «(добавлен человеком»; заметка `notes[]` формы «предупреждение прочитано: <раздел>» — флаг «прочитано» у строки `предупреждение` файла атаки (изменение `attack-warning-read`): раздел дословно из столбца «Раздел», текст — отдельный сегмент заметки через « · » (от начала или после « · » до конца или до следующего « · »), пробельные последовательности схлопываются; новое значение в свободном тексте заметки, номер контракта не растёт — плагин, не знающий формы, показывает заметку как заметку;
- пути файлов изменения, в том числе страница `symphysis.html`;
- поля `file_links` и `skills` в выводе `view-json` и `step_help.py`: карта «путь — файл от корня проекта» и скиллы шага;
- поля `verdict` и `stale_scope` у страницы шага с вердиктом в выводе `step_help.py`: значение вердикта форка и строки состава устаревшего вердикта (те же, что `journal.py check` печатает с маркером `[..]`); у шагов без вердикта полей нет. Поля новые, номер контракта они не меняют (изменение `attack-stale-scope`);
- каталог `.symphysis/viewer/`: там черновики человека, а также `events.jsonl`, курсоры сессий и скрипт хука; инсталлятор обязан их не стирать;
- хук клиента: перед запросом человека он говорит агенту словами, что человек внёс решения кнопкой (изменение, хеш журнала до и после, файл ответа в `answers/`) и что журнал нужно перечитать, а внесённое второй раз не вносить; строка «Показаны не все» отсылает к `events.jsonl`, когда события не уместились; ещё одна строка говорит, что правили `scheme.md`, это только сигнал. От этих слов зависит агент, поэтому их смысл меняется как контракт; точный текст — в `hook/hook.py` плагина VS Code и в скилле просмотрщика;
- записи плагина в проекте: `.claude/settings.local.json`, `.opencode/plugins/`, `.git/info/exclude`;
- списки линз;
- формат `scheme.md`: файл в каталоге изменения, один блок mermaid.

**Что считается сменой.** Новое поле сменой не считается. Удаление, переименование, смена смысла и новое значение существующего поля считаются. Новое значение опасно само по себе: плагин считает развилкой всё, что не факт.

С номера 2 страница лежит в `symphysis.html`: плагин этого номера пишет её туда, и его коммит несёт `Needs:` на коммит ядра с этим номером.

С номера 3 в списке линз атаки артефактов третья — `trace-link` (F-55): новое значение поля «линза», строка с ней не «вне списка». Плагин этого номера держит её в своём списке линз, его коммит несёт `Needs:` на коммит ядра с этим номером.

С номера 4 адресат парковки и записи журнала — `агент` вместо `материалы` (изменение `parking-addressee-agent`): `материалы` читается только у старых журналов, строка `apply` с ним отвергается, `check` сигналит о нём. Плагин этого номера держит `агент` в своём списке адресатов, его коммит несёт `Needs:` на коммит ядра с этим номером.

С номера 5 в списке линз атаки артефактов четвёртая — `rule-compliance` (изменение `attack-lens-conventions`, F-17): новое значение поля «линза», строка с ней не «вне списка». Плагин этого номера держит её в своём списке линз, его коммит несёт `Needs:` на коммит ядра с этим номером.

С номера 6 строка `- тяжесть: <путь файла атаки> · <раздел> · «<утверждение>» → <тяжесть> — «<обоснование>»` — новая форма грамматики `apply` (изменение `attack-severity-buttons`): по ней `apply` переписывает ячейку тяжести и `status` файла атаки своего изменения (путь от корня проекта, как его показывает страница), журнал не меняется. Плагин этого номера пишет её со своих кнопок, его коммит несёт `Needs:` на коммит ядра с этим номером. Плагин старого номера при ядре 6 просит новый `.vsix` и ничего не добавляет.

**Номер при мерже.** В случае необходимости изменить номер контракта номер увеличивается как `<current_number>`+1, `<current_number>` берётся из `main` перед мержем в `main` (слово владельца, 2026-11-08). Номер ветки до мержа — предварительный: если `main` ушёл вперёд, второе влитое перенумеровывает `CONTRACT`, свой абзац «С номера N» и `Why:` мержа. Сценарии и тесты о номере пишут «не ниже N»; равенство текущему номеру держит один тест — `CONTRACT` равен наибольшему N абзацев. Исключение — номера 5 и 6, выданные до этого правила: `attack-severity-buttons` взяло 6 по резерву очереди, `attack-lens-conventions` влито вторым без перенумерации; ядра с номером 5 в `main` нет, номер 6 несут `268eb25` (без линзы `rule-compliance`) и `32bfca7` (с ней), поэтому плагин номера 6 несёт `Needs:` на `32bfca7`.

**Что делать при смене.** Номер контракта растёт, а коммит ядра называет смену в `Why:`. Ядро лежит в `.symphysis/tools/` каждого проекта, и его версия расходится с версией плагина. Поэтому `view-json` отдаёт номер контракта в поле `contract`, целым числом, а плагин сравнивает его со своим:

| Номер ядра | Что просит плагин |
| --- | --- |
| ниже ожидаемого или его нет | обновить инструменты symphysis |
| выше ожидаемого | поставить новую сборку плагина: `.vsix` у VS Code, у порта своя |

## Логика и показ

Ядро отвечает за правила записи: `apply`, `check`, схему журнала и вывод. Показ и сборка промпта у страницы и у плагина свои: перенос в ядро означал бы запуск Python на каждый символ.

Логика страницы и плагина уже расходится, и человек это принял. Поэтому контрактный тест проверяет результат: один черновик после `apply` даёт один журнал и со страницы, и из плагина. Тест живёт в плагине: ядро плагин не читает.

На странице доступны все виды слова. Удобства, такие как поиск, фильтры и оглавление атаки, есть только в плагине.

## Проверки при разработке

В одной сессии запускай выбранные группы последовательно. Сначала обычный pytest
ядра, затем браузерный pytest ядра, npm-набор инсталлятора и проверки плагина.
Переходи к следующей группе после завершения предыдущей.

Из корня ядра, в выбранной среде Python:

```powershell
python -X utf8 -m pytest
python -X utf8 -m pytest -n 2 -m browser
npm --prefix installer test
```

При локальной правке модуля укажи каталог его тестов, например
`python -X utf8 -m pytest anchors/tests` для `anchors/`. Для браузерной
правки можно указать каталог или файл в браузерной команде, например
`python -X utf8 -m pytest -n 2 -m browser viewer/tests` для просмотрщика.
Общие и сквозные проверки, затронутые правкой, добавляй по их тестовым
входам. При правке инсталлятора или состава поставки включи npm-набор.

Активируй среду Python до pytest и сохрани её до завершения npm. Если
выбираешь интерпретатор абсолютным путём, помести каталог его `python`
или `python.exe` в начало PATH текущей сессии. Перед npm проверь
`python -c "import sys, yaml; print(sys.executable)"`. Путь в выводе должен
совпадать с интерпретатором ядра.

В VS Code запускай `npm test` из дерева плагина. При правке только одного
модуля можно выполнить `node build.mjs --unit`, затем
`node --test out/test/ИМЯ.test.js` для нужных файлов из `src/<модуль>/test/`.
При совместной или контрактной проверке передай абсолютный путь к выбранному
дереву ядра в `SYMPHYSIS_ROOT`. Для GIGA IDE выполни Kotlin-тесты по
`docs/start.md` в его репозитории. Для OpenCode запусти `npm test` из
репозитория порта. Оба порта следуют тому же ручному порядку.

Если модуль начинает использовать другой модуль, добавь в frontmatter его
`README.md` запись `dependencies` с именем репозитория
(`symphysis-core` или `symphysis-vscode`) и именем из поля `name` README
зависимости. Планировщик использует эти связи, чтобы добавить тесты прямых
и транзитивных потребителей.

Чтобы посмотреть адресный план из дерева ядра, явно укажи базу сравнения
каждого дерева, правки которого нужно учесть:

```powershell
python -X utf8 tools/run_tests.py plan change --core-root X:/core-worktree --core-base main --vscode-root X:/vscode-worktree --vscode-base main
```

Для одного коммита используй `plan commit` и `--core-commit` либо
`--vscode-commit`. У merge-коммита явно задай ревизию родителя через
`--core-parent` либо `--vscode-parent`. Корень, переданный без ревизии,
служит стендом для связанных проверок. Если план выбирает проверку плагина
на настоящем ядре, передай оба корня. Для стенда без сравнения используются
текущие декларации модулей. При переносе или удалении входа в сравниваемом
дереве план дополнительно читает прежние объявления.

При интеграции выполни адресный план, заменив `plan` на `run`.
Команда запускает выбранные группы в том же порядке и останавливается
на первой ошибке или недоступной обязательной проверке. В режиме
`run commit` коммит определяет состав, а проверяется выбранное рабочее
дерево. Отчёт указывает его HEAD и наличие рабочих правок.

Для полного прогона на выпуске или по решению владельца используй
`run full` с явными корнями. Для выпуска VS Code добавь `--release`
и передай worktree `main` ядра. Команда включает штатные локальные
e2e, в том числе `e2e:vsix`. Native-приёмка `npm run e2e:hook` обращается
к моделям Claude Code и OpenCode, поэтому её запускают отдельно по
явному поручению. Если тестовый VS Code находится вне стандартного
пути, задай абсолютный путь к нему в `SYMPHYSIS_CODE`.

`--summary <новый-файл.json>` сохраняет статусы, счётчики и Git-ревизии
без вывода тестов и окружения. `--log-dir <новый-каталог>` сохраняет
локальные stdout, stderr и JUnit для разбора. В сводке обязательный
пропуск даёт незавершённый прогон. Две исторические проверки активного
изменения trace-graph учитываются как неприменимые, если оно
заархивировано. Проверка активных журналов неприменима, если подтверждено
их отсутствие. Коды команды: `0` — успех или пустое сравнение,
`1` — падение проверки, `2` — незавершённый прогон, `3` — ноль
выполненных проверок.

## Выпуск

Каждый проект ставит тег в свой `main`. У ядра это `v1.x.x` и далее. У плагина тег равен версии в его файле сборки: `package.json` у VS Code, `build.gradle.kts` у GIGA IDE; к первому выпуску версия поднимается до 1.0.0.

Перед выпуском плагина:

1. Хеши из `Needs:` достижимы из `main` ядра: `git -C ../symphysis merge-base --is-ancestor <хеш> main`.
2. Тесты плагина с `SYMPHYSIS_ROOT` на worktree `main` ядра проходят без пропусков. Одной достижимости мало: `main` мог уйти вперёд, а без этой настройки тесты идут по той ветке, что стоит в `../symphysis`. Пропуски недопустимы: пропускаются как раз тесты на настоящем ядре, и опечатка в переменной даёт такой же зелёный итог.
3. У VS Code проходит `npm run e2e:vsix`.

## Рабочее дерево

- В `git add` идут только свои файлы.
- Своя ветка — свой worktree. В общем дереве ветку не переключают.
- Паузу объявляет только человек: сессии не видят друг друга.
- Только во время паузы идут операции над всей историей и команды, затирающие чужие незакоммиченные файлы: `git stash`, `reset --hard`, `clean`.

## Пуш

- Хук `pre-push` проверяет то, что уходит: содержимое и сообщения коммитов, которых на удалённом нет. Проверяют гейт имён и шаблон ключей задач. Агент пушит рабочие ветки только при установленном хуке, дисциплиной это правило не заменяется.
- Первый пуш каждого проекта из локального репозитория, `main` и перезапись истории идут только по слову человека. У плагина первым пушится `main`.

Хук стоит в `.git/hooks`, а не подключается относительным `core.hooksPath`: при относительном пути ветка старше хука в своём worktree пушится без проверки. Этот файл не версионируется, поэтому ставится отдельным шагом на каждой машине:

```
python tools/hooks/install_hooks.py --pre-commit
python tools/hooks/install_hooks.py --project ../symphysis-vscode
python tools/hooks/install_hooks.py --project ../symphysis-giga
python tools/hooks/install_hooks.py --project ../symphysis-opencode
```

Гейт один на машине: `X:\architecture-ways\tools\check_names.py`. Без него или без списка имён хук отказывает, а не пропускает. Разрешённые адреса и строки каждый проект держит в своих `tools/allowed-hosts.txt` и `tools/allowed-lines.txt`.

## Где живёт текст

В этом файле, в `main` ядра: иначе его видно не на всех ветках. `CLAUDE.md` каждого проекта ссылается сюда, копий нет.
