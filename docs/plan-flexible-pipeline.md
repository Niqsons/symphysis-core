## Зачем

Конвейер `gigacode-skills` (`change-intake` → `change-drafter` →
OpenSpec) держится на скриптах, которые компенсируют слабую модель
и узкий канал. Проверяем, можно ли на сильной модели заменить скрипты
соглашениями и пройти путь гибче.

Слабая модель ошибается громко: ломает формат, обрывает ответ.
Сильная — тихо: пишет связный правдоподобный текст без опоры.
Пример — playground v1 этой сессии: варианты в нём придуманы
до изучения материалов, развилки плоские, edge cases не учтены.

## Что убираем, что оставляем

**Убираем** — компенсацию слабой модели: формы на каждую единицу,
нарезку фактов по 25, ответ по одной секции, порции вопросов,
чек-лист, который пишет скрипт.

**Оставляем соглашениями** — то, ради чего скрипты существовали:

- у каждого варианта развилки — улика: путь к файлу и цитата;
- развилку решает человек; его слово записывается дословно;
- у человека спрашиваем только то, чего не прочитать в файлах;
- различаем **факт** (проверяется по материалам) и **развилку**
  (выбирается); факт не выдаётся за вариант выбора;
- состояние работы — в файлах, а не в контексте разговора:
  сессия длинная, контекст будет сжиматься.

### OpenSpec против sdd-superpowers — предварительно

По чтению исходников 2026-10-29, не по обкатке.

- **Брейншторм есть у обоих.** OpenSpec — `explore`: позиция без
  шагов, решения остаются в разговоре. sdd-superpowers —
  `sdd-brainstorm`: десять шагов, выход — `prd.md` и ADR, одобрение
  человека. Парковка есть только без адресата: `[NEEDS CLARIFICATION]`
  у sdd-superpowers, Open Questions в `design.md` у OpenSpec.
- **`propose` edge cases не ищет.** Спрашивает только о неясностях,
  которые «would materially affect scope, externally observable
  behavior, compatibility, or acceptance criteria», остальное —
  «make a reasonable assumption and record it» (`propose.js`).
  Ошибки и угрозы попадают в артефакты лишь через instruction
  в `schema.yaml`: «Inputs, outputs, and error conditions» в спеке,
  Risks в `design.md`, а сам `design.md` условный — «create only
  if any apply». `verify` сверяет код с артефактами после
  реализации, сами артефакты не атакует.
- **sdd-superpowers сильнее на шаг, не больше.** Error Scenarios
  в `spec.md` обязательны; `sdd-review` (режим A) спрашивает
  «edge cases missing? (empty states, error states, permission
  boundaries)». Категории общие: из списка шага 2 они, по оценке,
  ловят `../` и бинарные файлы. Остальное — модель угроз
  и жизненный цикл сессии, чек-листом не ловится.
- **Кастомизация.** OpenSpec — декларативно: граф артефактов
  в `schema.yaml`, `rules` по артефакту в `config.yaml`, instruction
  может передать работу скиллу (так `store-flow` зовёт `flow-step`);
  статус считает CLI по наличию файлов. sdd-superpowers — процесс
  в текстах скиллов и `routing.md`, держат его хуки; перестроить —
  значит переписать скиллы.

Кандидаты в решения — решение ниже, «Решение по основе»:

- основа — OpenSpec, sdd-superpowers — донор деталей: Error
  Scenarios, критерии Given/When/Then, руководства «Investigating
  a Decision», чек-лист `sdd-review` как нижняя планка атаки шага 7;
- журнал решений — артефакт схемы, от которого зависит `proposal`:
  тогда его видит `openspec status`, а `explore` пишет его
  по instruction;
- поиск edge cases — свой шаг (шаг 2 и атака шага 7), а не надежда
  на `propose`; в `propose` он входит через `rules` для `specs`
  и `design` или отдельным артефактом атаки.

**Проактивное проектирование в SDD-фреймворках** — OpenSpec,
sdd-superpowers, spec-kit, BMAD, GSD: разбор, сравнение и кандидаты
для конвейера — `docs/analysis/sdd-frameworks-proactive-design.md`.
Он поправляет пункт выше про `sdd-review`: жизненный цикл сессии
таксономии других фреймворков ловят.

**Расширяемость** — можно ли встроить playground и свой скилл
исследования, убрать шаг, поставить обязательную проверку без форка;
OpenSpec, sdd-superpowers, GSD, BMAD —

## Журнал решений — один файл на задачу

Все шаги читают его и пишут в него. Предлагаемое место —
`.gigacode/work/<задача>/decisions.md`. Начальный формат записи:

```markdown
## F-01 <вопрос>
- вид: развилка | факт
- статус: открыт | припаркован | решён
- адресат: материалы | человек | ИБ | архитектор
- зависит от: F-…
- варианты:
  - A. … — улика: `путь:строка` «цитата»
  - B. … — улика: …
- рекомендация: … — почему
- решение: … — слово человека дословно, дата
- следствия: …
```

Факт закрывается цитатой из материалов, развилка — словом человека.
Отвергнутые варианты не удаляются: они уходят в Risks `design.md`.

## Порядок

### 1. Брейншторм: концептуальные решения и парковка

- **Вход:** запрос, основа, заметки.
- **Делаем:** решаем самое концептуальное; неизвестное паркуем
  **с адресатом** — «материалы» или «человек / ИБ / архитектор».
  Без адресата следующий шаг получает «изучи материалы» без границ.
- **Выход:** журнал решений, первые записи.

### 2. Исследование

- **Вход:** записи журнала с адресатом «материалы».
- **Делаем:** читаем только под эти вопросы, отвечаем файлом
  с цитатами и путями; факт закрываем в журнале ссылкой на находку.
- **Выход:** `.gigacode/work/<задача>/research/*.md`, обновлённый журнал.
- **Известное к изучению:**
  - `.gigacode/materials/<плагин>/` — исходники плагина
    среды: реальный API плагинов вместо придуманных вариантов;
  - REST среды: валидация, выпуск на стенд, версии файлов;
  - что умеют IAM Proxy и MCP-клиент opencode: OAuth для удалённого
    сервера, elicitation, ресурсы;
  - вторая диаграмма v33 («Схема взаимодействия»), постановка LCAU,
    расшифровка GCAI.
- **Edge cases, которые v1 пропустил:**
  - данные проекта уходят в модель CLI-агента — вопрос К2/К3,
    в v33 закрытый «Не применимо», здесь снова применим;
  - несохранённые правки человека в открытой вкладке;
  - инъекции через содержимое файлов проекта;
  - токен истекает посреди работы агента; агент зацикливается
    на записи — нужны лимиты; несколько агентов на одном проекте;
  - бинарные файлы; пути с `../`;
  - функцию выключили посреди сессии; совместимость схем
    инструментов (в v33 API DSAI объявлен экспериментальным).

### 3. Второй круг брейншторма

- Решаем развилки, которые открылись после исследования.
- **Критерий выхода:** круг без новых решений и без новых фактов —
  стоп; исследование не больше двух кругов (как в `change-intake`).
  Остаток — в Open Questions.

### 4. Гриль-допрос по журналу

`mattpocock-skills:grilling` — допрос **человека** о решениях,
до того как написан текст: ошибка в решении сейчас стоит правки
журнала, после спецификации — переписывания.

### 5. Playground — просмотр журнала, а не источник вариантов

Переписать скилл под проектирование. Требования:

- **Варианты берёт из журнала**, не сочиняет. Шаблон-просмотрщик
  фиксированный, а не HTML с нуля на каждую задачу.
- **Показывает дерево:** зависимости (`зависит от`), варианты
  появляются по ним; факт без подтверждения закрывает развилки
  под собой.
- **Подсвечивает несовместимое.** Примеры из v1: «сервис от своей
  учётки» + «все инструменты» — сервис пишет в любой проект;
  «все права пользователя» + «подтверждает клиент» — выпуск
  на стенд без серверной проверки.
- **Покрытие** — согласованность решений, а не только закрыт ли
  пункт CR.
- **Замечания к схеме** и **промпт** — оставить, они в v1 сработали.
- **Результат — в файл, не в `localStorage`.** Браузер с `file://`
  писать на диск не умеет: выбрать способ — выгрузка файлом,
  File System Access API (только Chromium) или ответ вставкой в чат,
  который агент вносит в журнал.
- Без внешних зависимостей, как и сейчас.

### 6. Промпт → OpenSpec

- Промпт playground — **вход OpenSpec**, а не повод писать отдельную
  полную спецификацию: иначе одно и то же пишется дважды.
- Журнал ложится в `design.md` почти напрямую: решения — Decisions,
  отвергнутое — Risks, припаркованное — Open Questions.

### 7. Атака на артефакт

На готовом артефакте OpenSpec — проход «какое утверждение ничем
не подкреплено» (как гриль в `change-intake`). Это другой проход,
чем допрос на шаге 4.

## Как поймём, что обкатка удалась

Записывать по ходу, не по памяти в конце:

- утверждения без опоры — сколько и на каком шаге пойманы;
- развилки, оказавшиеся фактами, и наоборот;
- что пришлось переделывать и почему;
- где не хватило скрипта — кандидаты вернуть проверку в код.
